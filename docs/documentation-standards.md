# Стандарт классификации документации S.Center

## Назначение

Стандарт определяет, зачем документация классифицируется, как выбрать место для нового документа, какой файл считать источником истины и как сопровождать связи между требованиями, данными, кодом и пользовательскими сценариями.

Классификация нужна для предотвращения четырех системных проблем: дублирования требований, смешения текущей и будущей модели, накопления бессрочных планов и потери маршрута от продуктового решения к реализации. Она является постоянным процессом, а не разовой сортировкой файлов.

## Профиль документационной системы S.Center

Документация S.Center работает в смешанном режиме:

- `current` описывает наблюдаемую реализацию активного прототипа;
- `target` описывает утвержденный продуктовый или системный результат;
- `transition` описывает способ перехода и живет в активном плане;
- `history` сохраняет доказательство решения, но не управляет текущим поведением.

Текущий прототип построен на обычных `<script>`, IIFE и публичных `window.*`, не использует сборщик и не имеет `package.json`. Точка входа — `index.html`, локальный запуск — `node scripts/serve-prototype.mjs 8000`. Синтаксис JavaScript проверяется через `node --check`, автоматические тесты — через `node --test` для существующих `*.test.mjs`.

При установлении факта применяется следующая последовательность:

1. Текущая команда пользователя и действующие проектные инструкции определяют границы задачи.
2. Утвержденный продуктовый или системный владелец определяет, как система должна работать.
3. Активный runtime, его локальный README, `component-map` и `system-compliance-matrix` подтверждают, что реализовано сейчас.
4. Расхождение current и target фиксируется явно и не устраняется подменой одного временного слоя другим.
5. Roadmap и активные планы описывают будущую реализацию, но не подтверждают наличие runtime.
6. Evidence подтверждает приемку, reference помогает анализу, а archive сохраняет историю; ни один из этих слоев не создает требования самостоятельно.

`legacy/isolated/**` и временные методологические материалы не входят в обычный контекст. Их можно читать только для прямо поставленной задачи на аудит, восстановление, повторную интеграцию или перенос применимого механизма.

## Обязательные признаки документа

Каждый новый или существенно изменяемый документ должен иметь однозначно определимые признаки:

| Признак | Допустимые значения |
| --- | --- |
| Тип | управляющий документ, продуктовая спецификация, системная спецификация, спецификация данных, паспорт слоя, feature-паспорт, паспорт компонента, контрольный документ, план, roadmap, решение, справочный материал, доказательство проверки, архив |
| Авторитетность | основной, дополняющий, рабочий, доказательный, ненормативный |
| Временной слой | текущая реализация, целевая модель, переходное состояние, история |
| Уровень | проект, система, слой, feature, компонент, локальный элемент |
| Жизненный статус | черновик, актуален, требует проверки, заменен, архивный |
| Связность | родительский документ, дочерние документы, код, данные, сценарии, карты и матрицы |
| Следующее действие | оставить, уточнить, связать, разделить, объединить, переместить, архивировать, кандидат на удаление |

Один документ может затрагивать несколько временных слоев только при явном разделении разделами или таблицами. Необозначенное смешение текущего состояния, целевого требования и истории считается дефектом документации.

## Иерархия источников истины

| Вопрос | Основной источник |
| --- | --- |
| Правила работы с проектом | `PROJECT_GUIDELINES.md` |
| Правила работы AI-агентов | `AGENTS.md` |
| Навигация и классификация документов | `docs/README.md` и этот стандарт |
| Назначение и продуктовая рамка S.Center | `docs/system-overview.md` |
| Роли и потребности пользователей | `docs/user-roles.md` |
| Права и видимость | `docs/access-control.md` |
| Сущности, атрибуты и связи | `docs/entity-model.md` |
| Текущая реализация и расхождения | `docs/system-compliance-matrix.md` |
| Топология компонентов, данных и сценариев | `docs/component-map.md` |
| Каскадное влияние изменений | `docs/component-impact-map.md` |
| Будущая реализация | `docs/plans/system-scaling-roadmap.md` |
| Правила планирования задач | `docs/plans/README.md` |
| Текущий контракт слоя | README соответствующего каталога `src/` |
| Текущий пользовательский сценарий | `src/features/<feature>/README.md` |
| Текущий локальный UI-контракт | `src/components/<component>/README.md` |

Дополняющий документ не должен переопределять основной источник. Если документы расходятся, расхождение фиксируется в `docs/system-compliance-matrix.md`, а исправление направляется в основной источник.

## Маршрутизация нового документа

Перед созданием документа нужно:

1. Найти соответствующую строку или группу в `docs/README.md`.
2. Проверить, нельзя ли дополнить существующий основной источник.
3. Определить один тип, один основной временной слой и уровень документа.
4. Указать родительский источник и связанные реализации.
5. Для плана определить уровень сложности и жизненный цикл по `docs/plans/README.md`.
6. После создания добавить документ в реестр `docs/README.md` и, если меняется связность системы, в `docs/component-map.md` или `docs/component-impact-map.md`.

Новый самостоятельный документ оправдан, если у него есть отдельный владелец смысла, жизненный цикл или область обновления. Новый файл не создается только ради копирования выдержек из нескольких источников.

## Рекомендуемый заголовок метаданных

Для новых планов, аудитов, справочных и переходных документов после заголовка рекомендуется указывать:

```md
Тип: `план`
Статус: `актуален`
Временной слой: `переходное состояние`
Основной источник: `docs/...`
Связанные области: `src/...`, `docs/...`
Условие закрытия: `...`
```

Для локальных README эти сведения могут следовать из стандартной структуры разделов и расположения файла, но назначение, границы ответственности, данные, состояния, публичный интерфейс, связи и условие обновления должны быть явными.

## Формат component- и feature-паспортов

Паспорт описывает внешний контракт объекта, а не пересказывает построчно DOM, CSS или реализацию функций.

Простой локальный компонент сохраняет один `README.md` и в объеме, соответствующем его сложности, отвечает на вопросы:

1. Каково назначение и где проходит граница компонента?
2. Какие файлы кода и стилей реализуют контракт?
3. Какие входы и внешние участники обязательны?
4. Какова текущая структура и видимое содержимое?
5. Как компонент ведет себя и какие продуктово значимые состояния имеет?
6. Какие сценарии, проверки и документы нужно обновить вместе с ним?

Сложный component или feature дополнительно разделяет `Текущую реализацию` и `Будущую модель` и фиксирует:

- пространственный контракт: контейнер, привязка, размеры, stacking, overflow, правила узкого viewport;
- открытие, закрытие, focus/keyboard и конечное состояние каждого выхода;
- межкомпонентные контракты в форме `источник → условие → результат → получатель`;
- данные, состояния, ошибки и недоступность;
- минимальную ручную приемку и ссылки на автоматические тесты;
- visual reference или evidence только с указанием их ненормативного или доказательного статуса.

Файлы `01/02/03` не являются обязательными. Разделение паспорта допускается только если один README содержит несколько независимо изменяемых зон с разными владельцами или жизненным циклом. Пустые разделы ради единообразия не создаются.

Общая семантика состояний принадлежит `docs/component-states.md`; конкретный перечень состояний и переходов принадлежит локальному паспорту. Сущность и ее связи принадлежат `docs/entity-model.md`; feature-specific view model и визуальное представление принадлежат локальному feature- или component-паспорту.

## Правила связности

- Продуктовая спецификация связывается с системными спецификациями и матрицей соответствия.
- Системная спецификация связывается с сущностями, сценариями, картой компонентов и roadmap.
- Feature-паспорт связывается с `src/app`, `src/data`, используемыми компонентами и контрольными картами.
- Паспорт компонента связывается с feature-потребителями, данными и состояниями.
- План связывается с постоянными документами, которые должны быть обновлены после выполнения.
- Доказательство проверки подтверждает конкретный контракт, но не заменяет его.
- Справочный материал не становится техническим заданием без прямого решения пользователя.
- Архивный документ не используется как описание текущего состояния.

## Текущая и будущая модель

Текущая реализация фиксируется в локальных README, `docs/component-map.md` и `docs/system-compliance-matrix.md`. Будущие требования фиксируются в `docs/plans/system-scaling-roadmap.md` и конкретных планах. Целевые сущности могут быть описаны в `docs/entity-model.md`, если они явно отделены от демонстрационных данных прототипа.

Завершенный план не становится источником истины текущего поведения: его результат переносится в постоянные паспорта, карты и матрицу, после чего план архивируется.

## Автоматическая проверка

Команда `node scripts/check-documentation.mjs` проверяет воспроизводимые структурные инварианты: относительные Markdown-ссылки, реестр владельцев, реестры планов, наличие локальных README, visual assets, точные дубли, пути к реализации и минимальный состав пилотных сложных контрактов.

Checker не определяет продуктовый смысл и не исправляет документацию автоматически. Его диагностика должна называть файл, класс нарушения и постоянного владельца, после чего агент или автор вносит осознанное изменение. Критические классы checker покрываются отрицательными тестами в `scripts/check-documentation.test.mjs`.

Проверка запускается после создания, перемещения, архивирования или удаления документа, а также перед завершением комплексной документационной задачи. Предупреждение требует оценки, ошибка блокирует приемку.

## Проверка при изменениях

При изменении документа нужно проверить:

- сохранен ли один основной источник для затронутого аспекта;
- не смешаны ли временные слои;
- существуют ли все исходящие ссылки;
- обновлены ли связанные README, карты и матрица;
- вынесено ли будущее требование в roadmap;
- отражен ли новый документ в `docs/README.md`;
- не остался ли завершенный план в активном списке без условия закрытия.
- проходит ли `node scripts/check-documentation.mjs`.

## Архивирование и удаление

Документ можно архивировать, если его задача завершена, результат перенесен в постоянные источники и исторический контекст все еще полезен. Документ является кандидатом на удаление, если он заменен, не содержит уникального знания и не нужен для аудита.

Перед удалением обязательно проверяются входящие ссылки, уникальность содержания, наличие преемника и отсутствие зависимости активной реализации. Пометка `кандидат на удаление` сама по себе не разрешает удаление.

Комплексные проверки структуры выполняются по отдельному временному плану в `docs/plans/` согласно `docs/plans/README.md`. После приемки временный план удаляется, а доказательный результат сохраняется в `docs/audits/`.
