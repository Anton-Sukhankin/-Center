# Обзор системы S.Center

## Назначение

Личный кабинет S.Center предназначен для централизации разрозненной проектной информации, оперативного выявления проблем и своевременного принятия управленческих решений.

Система помогает руководителю проекта не просматривать вручную множество источников, а быстро увидеть, что происходит в выбранном бизнес-юните, проекте или очереди, какие события требуют реакции и как они связаны с ключевыми показателями.

## Управленческая задача

Главная задача системы — собрать проектный контекст в одном окне и помочь пользователю сфокусироваться на важных отклонениях.

В текущей рабочей среде информация о проекте находится в разных продуктах, графиках и учетных системах. Руководителю сложно быстро обработать весь массив данных и понять реальное состояние стройплощадки. S.Center должен снять часть этой нагрузки: собрать данные, показать события, связать их с показателями и подготовить основу для решения.

## Основные инструменты

| Инструмент | Роль в системе |
| --- | --- |
| Единое окно данных | Собирает статические метрики проекта и оперативные события из разных источников. |
| Контекстное дерево | Позволяет переключаться между бизнес-юнитом, проектом и очередью. |
| Лента событий | Показывает ежедневные инциденты и отклонения, разделенные по приоритету. |
| Метрики | Отражают финансовые и строительные показатели выбранного контекста. |
| Фильтрация | Помогает сузить выдачу событий по источникам, метрикам, периодам и приоритету. |
| ИИ-аналитика | Анализирует массив событий, подсвечивает проблемные зоны, описывает риски и предлагает действия. |

## Структурный контекст

Главным структурным контекстом работы пользователя по умолчанию является проект. В базовом состоянии интерфейс показывает шапку проекта с ключевыми атрибутами: стадией строительства, бизнес-юнитом, кластером и руководителем проекта.

Бизнес-юнит и очередь служат для изменения масштаба фокуса. Бизнес-юнит поднимает пользователя на уровень агрегированной картины по группе проектов. Очередь опускает пользователя на уровень конкретной фазы строительства, чтобы отделить актуальную стройку от будущих или менее релевантных этапов.

Операционный фокус внутри выбранного контекста находится на событиях. Метрики нужны прежде всего для объяснения влияния событий на проект, а не как самостоятельный статический центр интерфейса.

## Ролевая адаптация

S.Center создается для разных участников строительного процесса. Интерфейс должен адаптироваться под роль и права пользователя: менять доступные проекты, ленту событий, дерево метрик, видимость финансовых данных и набор доступных действий.

Ключевая аудитория — руководители проектов, но система также должна поддерживать верхнеуровневый просмотр для топ-менеджмента и акционеров, фокус на графиках для планировщиков, работу с событиями площадки для контрольных служб и ограниченный доступ для внешних подрядчиков.

Подробная ролевая модель описана в `docs/user-roles.md`.

## Оперативный фокус

Финансовые метрики обычно обновляются с низкой частотой, например раз в месяц. Оперативные события появляются постоянно: изменение даты выдачи РНС, невыход рабочих, штрафы подрядчикам, сдвиги графиков, отклонения в работах.

Поэтому система должна разделять два уровня информации:

- стабильные показатели проекта;
- ежедневные события, требующие внимания.

Основной пользовательский фокус находится на событиях, потому что именно они помогают вовремя заметить проблему до того, как она станет крупным отклонением в метриках.

## Продуктовый приоритет

В системе выше всего ценится цепочка `приоритизированное событие → риск → управленческое действие`.

Статический мониторинг показателей остается важным, но не является главным смыслом продукта. Метрики помогают объяснить влияние событий, а не заменяют работу с оперативными инцидентами. Система должна автоматически поднимать критичные события наверх, скрывать второстепенный шум и помогать пользователю быстро перейти к решению.

## Выявление отклонений и рисков

S.Center должен не только показывать данные, но и переводить оперативные события в понятные риски.

Событие может влиять на нижнюю метрику, например расходы на строительство, и на верхнеуровневый показатель проекта, например чистую прибыль. Такая связь нужна, чтобы пользователь видел не только факт инцидента, но и его возможные последствия для проекта.

## Роль ИИ-аналитики

ИИ-аналитика является одним из ключевых смысловых элементов системы.

Пользователь не должен самостоятельно искать связи между десятками карточек событий. Система должна помогать выявлять повторяющиеся проблемы, риски и зависимости: например, регулярные срывы подрядчика, вероятность кассового разрыва, накопление отклонений по срокам или рост влияния на финансовые показатели.

Результат ИИ-аналитики должен быть прикладным:

- краткое описание проблемной зоны;
- объяснение риска;
- связь с событиями и метриками;
- список возможных действий, например создать задачу или запросить объяснения.

После работы с событием или ИИ-аналитикой пользователь должен выбрать управленческую реакцию: создать задачу, запросить объяснения, связаться с подрядчиком, перейти в график работ или изменить информационный фокус карточки. Подробно этот сценарий описан в `docs/decision-actions.md`.

## Граница системы

S.Center не должен быть просто BI-дашбордом или хранилищем отчетов. Его ценность не только в отображении показателей, а в соединении проектного контекста, событий, метрик и рекомендаций.

Система должна помогать проектной команде быстрее понять, где требуется реакция, и снизить риск запоздалого управленческого решения.

## Что важно не потерять при развитии

- Данные должны собираться в едином контексте: бизнес-юнит, проект, очередь.
- События должны быть связаны с метриками и источниками.
- Пользователь должен видеть приоритетные события без лишнего анализа.
- Метрики должны объясняться через события, а не существовать отдельно от них.
- ИИ-аналитика должна давать не декоративный текст, а управленчески применимые выводы.
- Документация должна фиксировать связь `данные → событие → метрика → пользовательское решение`.
