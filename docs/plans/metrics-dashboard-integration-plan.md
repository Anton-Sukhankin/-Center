# План: центральный дашборд раздела «Метрики»

Документ подчиняется регламенту `docs/plans/README.md`.

Статус: `этап 1 реализован — UI, demo-данные и переключение проектов`.

Уровень сложности: `сложная задача`.

## Goal

Заменить текущую заглушку сегмента `Метрики` полноценным центральным дашбордом, который:

- показывает контрольные этапы, сроки и бюджет выбранного проекта;
- обновляется при выборе проекта внутри бизнес-юнита в левом дереве;
- не сохраняет на экране значения предыдущего проекта во время смены контекста;
- связывает отклонения метрик с влияющими на них событиями;
- остается читаемым в фактической ширине центральной области S.Center;
- использует единый слой демонстрационных данных и расчетов;
- не возвращает изолированный правый блок метрик из `legacy/isolated/`.

## Context

### Текущая реализация

- Сегмент `Метрики` уже присутствует в `EventToolbar`.
- При выборе сегмента `Метрики` табы приоритета скрываются, а `priority-events-container` показывает заглушку `Раздел в разработке`.
- Выбор бизнес-юнита, проекта или очереди обновляет `window.activeContext`, события и `window.metricsData`.
- `src/data/app-data.js` уже рассчитывает:
  - дерево финансовых метрик с `fact`, `plan`, `forecast`, `delta`, `deltaPrevMonth`;
  - строительную длительность и объем для очереди, проекта или бизнес-юнита через `getConstructionMetricsForContext()`.
- Текущие финансовые значения агрегируются из демонстрационных влияний событий, поэтому не являются источником договорного бюджета.
- Текущая `getConstructionMetricsForContext()` складывает длительности очередей. Такая сумма не равна календарной длительности проекта или критическому пути и не может напрямую заполнять карточки референса без отдельной методики.
- Текущая модель не содержит полного набора данных референса: календаря контрольных этапов, дат начала и завершения проекта, трех бюджетных оснований `ЦП` / `ДУ` / `КС2`, времени обновления и качества источника.
- Правый блок метрик и drawer структуры отсутствуют в активном интерфейсе и изолированы в `legacy/isolated/`. Самостоятельный BI-график позднее возвращен в `src/features/bi/` только для перехода из детальной карточки события и не входит в центральный MetricsDashboard.

### Сильные стороны

1. Верхняя временная шкала сразу объясняет положение проекта между завершёнными и будущими этапами.
2. Основные категории разделены на календарный и бюджетный блоки.
3. Крупные числа и единицы измерения визуально отделены от поясняющего текста.
4. Сетка карточек и повторяемые паттерны позволяют быстро сравнивать показатели.
5. Синие, фиолетовые и красные акценты не перегружают преимущественно нейтральный фон.
6. В бюджетных карточках одновременно показаны относительное и абсолютное отклонения.

### Недостатки и риски

| Приоритет | Наблюдение | Почему это проблема | Рекомендация |
| --- | --- | --- | --- |
| P0 | В данных сроков есть видимое расхождение: `30.11.2028 + 18 дней = 18.12.2028`, но отдельная карточка показывает `19.12.2028`. | Пользователь не понимает, какая дата является канонической и применяется ли включительный подсчет. | Хранить исходные даты и единое правило календаря; длительность, дельту и прогноз вычислять централизованно. |
| P0 | `986 дней` не соответствует календарному интервалу `15.01.2025–30.11.2028`: это 1415 дней без включения конечной даты, 1416 с включением или 1012 будних дней без учета праздников. | Не определена база расчета: календарные, рабочие или производственные дни. | Сохранить обязательное поле `durationBasis` и методику в модели данных; по текущему UI-решению не повторять служебную подпись `календарных дней` внутри карточки. |
| P0 | Название `Расчетная (фактическая) длительность` соединяет два разных смысла, хотя проект по шкале еще не завершен. | Фактическая длительность возможна только после завершения; до него это прогноз. | Использовать `Прогнозная длительность`, а после завершения переключать карточку на `Фактическая длительность`. |
| P1 | Контекст проекта должен оставаться заметным при переключении левого дерева. | Дублирование названия проекта и даты обновления внутри дашборда создает лишний визуальный уровень. | Использовать существующую шапку проекта как единственный видимый контекст; локальный статус данных показывать только при `stale`, `partial` или `error`. |
| P1 | Девять этапов растянуты на ширину около 1670 px. | В центральной области S.Center с левой панелью подписи будут сталкиваться или станут слишком мелкими. | На обычной ширине показывать фокусное окно вокруг текущего этапа и действие `Все этапы`; на широком экране — полную шкалу. |
| P1 | Состояния шкалы различаются в основном цветом и типом линии. | Пользователи с нарушением цветового восприятия могут не различить завершённое, текущее и будущее состояния. | Добавить иконку/маркер, текстовый статус и доступное имя каждого этапа; цвет использовать как дополнительный сигнал. |
| P1 | Красный и зеленый применены как универсальные `плохо` / `хорошо`. | Для затрат, принятых работ и сроков смысл роста зависит от типа показателя. | Рассчитывать семантический статус по правилам метрики: `favorable`, `unfavorable`, `neutral`, `unknown`; рядом показывать знак и текст. |
| P1 | Попарные сравнения `ЦП`, `ДУ`, `КС2` повторяются во всех трех карточках. | Повторение повышает плотность, но позволяет считать каждое основание автономно. | Для текущего этапа по решению пользователя сохранить по два сравнения внутри каждой карточки и выстроить нижний блок как ровную двухколоночную матрицу; к сокращению возвращаться только после проверки на реальных данных. |
| P1 | Служебные счетчики влияющих событий перегружают компактную сводку сроков. | Карточки должны быстро сообщать значение и детализацию, не смешивая их с отдельным сценарием анализа событий. | По текущему решению не показывать `N событий влияют` внутри KPI-карточек; связь сохранить в данных и раскрывать отдельным аналитическим сценарием. |
| P2 | Нет расшифровки `ЦП`, `ДУ`, `КС2`, `РНС`, `РиВ`. | Термины могут быть неоднозначны для новой роли или другого бизнес-юнита. | Показывать полное название в подписи или tooltip; сокращение оставить в заголовке. |
| P2 | Не видны состояния `loading`, `empty`, `error`, `stale`, `restricted`. | При смене проекта или отсутствии интеграционных данных интерфейс может показать старые либо ложные нули. | Спроектировать эти состояния до верстки и запретить подменять отсутствие данных значением `0`. |
| P2 | Все карточки почти одинаково акцентны. | Критическое отклонение `+18 дней` конкурирует с нейтральными справочными значениями. | Первый экран должен начинаться с 3–4 управленческих сигналов, затем переходить к деталям. |
| P2 | Серые подписи и тонкие границы выглядят малоконтрастными. | Возможен риск недостаточного контраста и плохой читаемости на слабом мониторе. | Проверить контраст по WCAG 2.2 AA; вспомогательный текст не делать меньше 12 px. |
| P2 | Фазовая навигация занимает всю строку и не имеет видимого overflow-сценария. | На меньшей ширине часть разделов может стать недоступной. | Использовать горизонтальный скролл с видимым продолжением или меню переполнения; сохранить клавиатурное управление. |

### Итог аудита

Референс подходит как источник состава данных и общей композиции, но не должен переноситься буквально. Для S.Center требуется:

- более явная иерархия `контекст → управленческий сигнал → детализация`;
- расчетно согласованные даты и длительности;
- адаптация временной шкалы под более узкую центральную область;
- связь проблем с событиями в данных и аналитических сценариях без служебных счетчиков внутри KPI-карточек;
- системные состояния данных и доступности.

## Целевая информационная архитектура

### Уровень 1. Контекст и состояние данных

Шапка проекта является единственным постоянным подтверждением активного контекста. После внутренних вкладок дашборда сразу начинается сводка показателей.

Дата обновления и локальный статус не показываются в нормальном состоянии. Отдельное уведомление появляется только для значимых состояний `stale`, `partial`, `error` или `restricted`, когда пользователю действительно нужно оценить надежность данных.

### Уровень 2. Подразделы метрик

Сохранить категории референса как внутреннюю навигацию дашборда:

- `Общие`;
- `Проектирование`;
- `Тендеры и контрактация`;
- `Продажи`;
- `СМР`;
- `Приемка и заселение`.

Первый этап реализации наполняет `Общие`. Остальные вкладки получают корректное состояние `Раздел готовится` только если для них еще нет согласованных данных. Они не должны показывать данные `Общие` под другим названием.

Строка внутренних вкладок повторяет визуальный контракт табов приоритета событий: располагается на белой подложке на всю ширину центральной области, без зазора примыкает к `EventToolbar`, использует горизонтальный `padding: 22px`, текст `14px`, темный активный текст и нижний индикатор высотой `4px`. При прокрутке дашборда строка остается у верхней границы рабочей области; на узкой ширине допускается горизонтальный скролл. Переключение вкладки не должно перемонтировать строку навигации и весь дашборд: обновляются только состояния вкладок и содержимое постоянного `tabpanel`, без повторного запуска входной анимации и потери фокуса.

### Уровень 3. Управленческая сводка

В первой строке показывать четыре карточки:

1. `Плановая длительность`.
2. `Прогнозная / фактическая длительность`.
3. `Отклонение срока`.
4. `Прогнозная дата завершения`.

Правила:

- каждая карточка состоит из верхней секции главного значения и нижней секции детализации;
- верхняя секция повторяет композиционный контракт бюджетных карточек: слева располагается подложка с иконкой, справа в одной колонке — название и главное числовое или календарное значение;
- верхняя и нижняя секции имеют единый внутренний `padding: 20px`; высота верхней секции рассчитывается из содержимого без искусственного `min-height`, а горизонтальная граница занимает всю ширину карточки;
- сама KPI-карточка не имеет `min-height` на desktop- и mobile-ширине; итоговая высота определяется содержимым строки;
- единица измерения всегда подписана;
- критическая карточка имеет status chip, а не только красный цвет;
- каждая карточка содержит один основной показатель и не более двух поясняющих строк;
- счетчики и действия `N событий влияют` внутри KPI-карточек не отображаются;
- связь метрик с событиями сохраняется в данных и может раскрываться отдельным аналитическим сценарием.

### Уровень 4. Контрольные этапы

Порядок:

1. Текущий этап.
2. Два предыдущих и два следующих этапа на обычной ширине.
3. Полная шкала на широком экране или после действия `Все этапы`.

Каждый этап содержит:

- название;
- плановую дату;
- прогнозную или фактическую дату при наличии;
- статус `Завершён`, `Текущий этап`, `Запланирован`, `Есть задержка`;
- величину отклонения, если она не равна нулю.

### Уровень 5. Бюджет

Три основные карточки:

- `ЦП` — целевая стоимость проекта по сметной документации;
- `ДУ` — объемы действующих договоров и дополнительные соглашения;
- `КС2` — фактически принятый объем работ по актам КС2.

Каждая карточка состоит из двух самостоятельных секций:

- верхняя секция показывает основание, значение и расшифровку;
- нижняя секция показывает два попарных сравнения с остальными основаниями;
- высота верхней секции определяется ее содержимым и внутренним `padding: 20px` без фиксированного `min-height`;
- интервал между названием бюджетной карточки и сводным значением совпадает с карточками сроков и задается единым токеном `6px`;
- подложка иконки в бюджетных карточках имеет размер `58×58px`, сама иконка — `24×24px`;
- верхняя секция имеет внутренний `padding: 20px`, а контейнер нижней секции — `padding: 0` и сплошную горизонтальную границу на всю ширину карточки;
- две самостоятельные ячейки сравнений имеют собственный `padding: 20px`, разделены вертикальной границей на всю высоту нижней секции и используют единый порядок данных.

Все KPI-, бюджетные карточки и карточка контрольных этапов отображаются без внешней тени; границы карточек сохраняются.

### Уровень 6. Объяснение через события

Связь метрик с событиями сохранять в модели данных и отдельном аналитическом сценарии, но не выводить в верхних KPI-карточках счетчики, подписи или списки влияющих событий. Переход к причинам отклонения должен быть самостоятельным действием вне двухсекционных карточек сроков.

Так карточки остаются компактной сводкой, а продуктовый принцип `метрика объясняется событиями` реализуется без перегрузки их нижних секций.

## Поведение активного контекста

### Основной сценарий

1. Пользователь выбирает проект в левом дереве.
2. `setActiveEntity()` обновляет `window.activeContext`.
3. Слой данных строит `MetricsDashboardViewModel` для выбранного `projectId`.
4. Дашборд сначала переходит в `loading`, затем атомарно заменяет все значения.
5. Если пользователь уже находится в сегменте `Метрики`, повторный клик не требуется.
6. Внутренняя вкладка дашборда сохраняется, если она доступна в новом проекте; иначе выбирается `Общие`.

### Другие уровни дерева

Первый критерий приемки относится к проектам. Для выбора бизнес-юнита или очереди нельзя оставлять значения предыдущего проекта.

- Бизнес-юнит: до отдельного согласования портфельной версии показывать состояние `Выберите проект для просмотра дашборда`.
- Очередь: показывать состояние `Дашборд доступен на уровне проекта` с действием перехода к родительскому проекту либо использовать отдельную очередь только после согласования состава ее метрик.

Такой fallback намеренно отличается от текущей расчетной способности `appData` агрегировать метрики: наличие арифметики не означает, что проектные даты и бюджетные основания можно методологически корректно агрегировать.

```js
  name: 'Начало заселения 1 очереди',
  plannedDate: '2026-10-01',
  forecastDate: null,
  actualDate: null,
  status: 'current',
  source: 'Gantt',
  updatedAt: '2026-07-24T10:30:00+03:00'
}
```

Статус не должен вручную противоречить датам. Слой данных вычисляет его из `plannedDate`, `forecastDate`, `actualDate` и текущей даты либо валидирует явное значение.

### Сроки

```js
{
  startDate: '2025-01-15',
  plannedFinishDate: '2028-11-30',
  forecastFinishDate: '2028-12-18',
  actualFinishDate: null,
  plannedDurationDays: 1415,
  forecastDurationDays: 1433,
  deviationDays: 18,
  deviationPercent: 1.27
}
```

Значения длительности, дельты и процента не должны храниться независимо, если их можно получить из исходных дат и `durationBasis`.

### Бюджетные основания

```js
{
  targetCost: {
    code: 'ЦП',
    name: 'Целевая стоимость проекта\nпо сметной документации',
    value: 18_600_000_000
  },
  contractedCost: {
    code: 'ДУ',
    name: 'Объемы действующих договоров\nи дополнительные соглашения',
    value: 19_400_000_000
  },
  acceptedWorks: {
    code: 'КС2',
    name: 'Фактически принятый объем работ\nпо актам КС2',
    value: 22_300_000_000
  }
}
```

Абсолютные и процентные отклонения рассчитываются одной функцией. В исходных данных не хранить шесть вручную заполненных парных сравнений.

### Что можно переиспользовать

| Источник | Использование |
| --- | --- |
| `window.activeContext` | Идентификатор и уровень выбранного контекста. |
| `window.metricsData` | Финансовое дерево и связь карточек событий с метриками. |
| `appData.getConstructionMetricsForContext()` | Только источник отдельных demo-значений очередей; суммарную длительность проекта нельзя использовать как календарный срок без изменения методики. |
| `appData.getEventsForContext()` | Список событий текущего проекта. |

- времени обновления, источника и статуса качества;

С учетом текущей архитектуры без ES-модулей достаточно одного осознанного интерфейса:

```js
  setSection(sectionId),
  destroy()
};
```

`src/app/app.js` остается владельцем активного контекста и передает готовое представление. Feature не вызывает `setActiveEntity()` и не меняет `window.metricsData`.

- заменить разметку `metrics-work-in-progress-state` вызовом feature;

### Изменения `EventToolbar`

В режиме `Метрики`:

- сегментный переключатель остается видимым;
- поиск событий скрывается;
- `Аналитика` и `Фильтр` событий скрываются, пока для метрик не определен отдельный сценарий;
- `Задать вопрос` остается доступной и получает контекст дашборда;
- изменение режима не должно смещать сегментный переключатель скачком.

## Адаптив и доступность

### Контрольные ширины

- `>= 1440px`: четыре KPI в строке, три бюджетные карточки в строке, полная шкала при достаточном месте.
- `1024–1439px`: две KPI в строке, бюджетные карточки `2 + 1`, фокусное окно шкалы.
- `< 1024px`: одна колонка или две компактные колонки по фактической ширине центральной области; внутренняя навигация прокручивается горизонтально.

Решение принимается по ширине контейнера, а не только viewport, потому что ширину меняют левая панель и drawer.

### Требования

- статус не кодируется только цветом;
- интерактивные цели не меньше `44×44px`, если контроль не является частью плотной табличной навигации;
- каждая вкладка и каждый этап имеют доступное имя и состояние;
- DOM-порядок совпадает с визуальным чтением;
- клавиатура может пройти внутренние вкладки, `Все этапы`, раскрытие сравнений и ссылки на события;
- фокус видим на светлом фоне;
- вспомогательный текст проходит WCAG 2.2 AA по контрасту;
- при 200% zoom основные значения и подписи не перекрываются.

- подключить файл в `index.html` до `src/app/app.js`.

Результат: один источник проектного дашборда.

### 3. Создать feature и статические состояния

- создать `src/features/metrics-dashboard/`;

- реализовать адаптив по ширине контейнера;
- подключить Lucide-иконки без рисования собственных SVG.

Результат: дашборд умеет безопасно отображать полный и неполный набор данных.

### 4. Интегрировать режим `Метрики`

- заменить заглушку в `renderEventFeed()`;
- добавить подготовку view model по `window.activeContext`;
- настроить `EventToolbar` для режима метрик;
- сохранить остальные сегменты и события без изменения.

Результат: сегмент `Метрики` показывает дашборд, а возврат к событиям восстанавливает прежний UI.

### 5. Связать дашборд с левым деревом

- проверить проекты внутри каждого бизнес-юнита;
- исключить flash старых значений при переключении;
- сохранить или сбросить внутренний раздел по описанному правилу;
- реализовать fallback бизнес-юнита и очереди.

Результат: все значения соответствуют выбранному проекту.

### 6. Связать метрики с событиями

- получить связанные события из общего слоя данных;
- не выводить счетчик и причины отклонения внутри верхних KPI-карточек;
- предусмотреть отдельный аналитический переход в событийный режим с фильтром по `metricId` вне карточек сроков;
- не создавать второй список Event внутри данных дашборда.

Результат: пользователь может перейти от отклонения к его причинам.

### 7. Провести визуальную и сценарную приемку

- сравнить верстку с референсом по составу данных, но не копировать его масштаб буквально;

- проверить все состояния данных.

Результат: дашборд читаем, доступен и не показывает несогласованные значения.

### 8. Синхронизировать документацию

- обновить паспорта feature и затронутых компонентов;
- обновить карты, матрицу, модель сущностей, состояния, data/app README;
- отметить реализованный объем и оставить будущие интеграции в roadmap.

Результат: текущая реализация и будущая модель описаны раздельно.

## Решение перед стартом реализации

Этап 1 выполнен с зафиксированными demo-допущениями: календарные дни, расчет без включения даты старта, прогнозная дата равна плановой дате плюс отклонение; для каждого из оснований `ЦП`, `ДУ`, `КС2` рассчитываются два сравнения с остальными основаниями. Реальные источники, методология и ролевые ограничения остаются следующим этапом.

До изменения кода нужно подтвердить три методологических пункта:

1. `986 / 1004 дней` считаются календарными, рабочими или производственными днями.
2. Каноническая прогнозная дата в примере — `18.12.2028` или `19.12.2028`.
3. Что именно означают `ЦП`, `ДУ`, `КС2` в целевой терминологии проекта и какой показатель является главным основанием сравнения.

Если подтверждения нет, для demo-реализации следует использовать явно обозначенное правило:

- календарные дни;
- расчет без включения даты старта;
- прогнозная дата вычисляется как `плановая дата + отклонение`;
- для каждой карточки `ЦП`, `ДУ`, `КС2` показываются два попарных сравнения, рассчитанные из трех исходных значений.
