# Модель сущностей интерфейса

## Цель

Этот документ фиксирует единый атрибутивный слой проекта. Модель системы разделяется на две группы: структурные сущности, которые задают организационный контекст и адрес данных, и информационные сущности, с которыми пользователь работает в интерфейсе.

Слой данных расположен в `src/data/app-data.js` и подключается до `src/app/app.js`. Проект остается на обычных `<script>`, без ES-модулей и без сборщика.

## Группы сущностей

| Группа | Назначение | Сущности |
| --- | --- | --- |
| Иерархия объектов | Формирует навигационное дерево и задает адрес для событий, метрик и пользовательского фокуса. | Бизнес-юнит, проект, очередь, этап, объект строительства. |
| Информационные и операционные сущности | Наполняют структурные объекты данными, отклонениями, выводами и действиями. | Событие, задача, ответственный, метрика, ТЭП, ИИ-вывод, действие. |

## Структурные сущности

| Сущность | Назначение | Ключевые признаки |
| --- | --- | --- |
| Бизнес-юнит | Верхний уровень навигации и агрегации. Объединяет проекты и показывает сводную картину по направлению. | Название, руководитель бизнес-юнита, дочерние проекты, агрегированные показатели. |
| Проект | Главный контекст работы пользователя по умолчанию. | Название, изображение, стадия строительства, бизнес-юнит, кластер, руководитель проекта, дочерние очереди. |
| Очередь | Нижний базовый уровень детализации интерфейса. Позволяет сфокусироваться на конкретной фазе строительства. | Название очереди, ссылка на проект, строительные показатели, события и метрики выбранной фазы. |
| Этап | Более глубокий уровень декомпозиции внутри очереди. Используется для точной адресации работ и событий. | Название этапа, связь с очередью, статус или период работ. |
| Объект строительства | Конкретный объект внутри проекта или очереди, например корпус, дом, паркинг или участок работ. | Тип объекта, название объекта, связь с очередью или этапом. |

## Информационные и операционные сущности

| Сущность | Назначение | Ключевые признаки |
| --- | --- | --- |
| Событие | Главная операционная сущность системы. Отражает инцидент, изменение, риск или уведомление, требующее внимания пользователя. | Источник, время, заголовок, описание, адрес возникновения, приоритет, связанная метрика, влияние. |
| Задача | Демонстрационная операционная сущность, создаваемая пользователем на основании события. | Название, описание, ответственный, статус, исходное событие, проект, даты создания и изменения. |
| Ответственный | Демонстрационная запись справочника участников проекта для назначения задачи. | ФИО, инициалы, роль, должность, email, пол, face-only avatar, команда, доступность, членство в проектах. |
| Метрика | Числовой показатель состояния проекта, очереди или бизнес-юнита. Может быть финансовой или строительной. | Факт, план, прогноз, отклонение, отклонение от предыдущего месяца, родительская и дочерние метрики. |
| ТЭП | Технико-экономический параметр объекта или очереди. Описывает физические и строительные характеристики. | Площадь, длительность, объемы работ, статусы и другие параметры масштаба строительства. |
| Группа работ | Demo-родитель первого уровня в таблице раздела `Объекты`. | `id`, код, название, вес, сроки, подрядчик, готовность, статус и признак дочерних строк. |
| Вид работ | Demo-дочерняя строка второго уровня, связанная с группой через `parentId`. | Код, название, вес, плановый срок `с/по`, подрядчик, готовность и статус. |
| ИИ-вывод | Результат анализа одного события или массива событий. Помогает пользователю понять причину, риск и возможные действия. | Описание проблемы, выявленные связи, риск, рекомендации, связь с событиями и метриками. |
| Действие | Управленческая или системная реакция пользователя на событие или вывод аналитики. | Создать задачу, запросить объяснение, связаться с подрядчиком, открыть график, закрепить, исключить, изменить приоритет. |

## Связь сущностей

Базовая цепочка данных:

```text
Бизнес-юнит
  -> Проект
    -> Очередь
      -> Этап / Объект строительства
        -> Событие
          -> Метрика / ТЭП
            -> ИИ-вывод
              -> Действие пользователя
          -> Задача -> Ответственный
```

На конкретном объекте строительства, входящем в очередь определенного проекта, происходит событие. Событие влияет на метрику или ТЭП, система формирует ИИ-вывод, а пользователь выбирает корректирующее действие.

Проект остается главным структурным контекстом по умолчанию. Бизнес-юнит агрегирует проекты, очередь изолирует данные конкретной фазы строительства, а событие остается главным ежедневным информационным фокусом пользователя.

В текущем прототипе одно событие может иметь несколько задач, а каждая задача связана ровно с одним событием и одним ответственным. Связь хранится через `Task.sourceEventId`, `Task.projectId` и `Task.assigneeId`.

## Сущность задачи

Текущая задача является in-memory сущностью интерфейсного прототипа и живёт до перезагрузки страницы. Создание, редактирование и удаление задачи работают только в пределах текущей страницы без постоянного хранения и истории изменений.

| Атрибут | Назначение |
| --- | --- |
| `id` | Уникальный runtime-идентификатор задачи. |
| `status` | Технический статус; при создании используется `new`, полноценный workflow пока отсутствует. |
| `title` | Обязательное название, до 128 символов. |
| `description` | Обязательное описание, до 4000 символов. |
| `assigneeId` | Обязательная ссылка на демонстрационного ответственного. |
| `sourceEventId` | Ссылка на событие-основание. |
| `projectId` | Проект исходного события. |
| `createdAt` | Дата и время создания в текущей сессии страницы. |
| `updatedAt` | Дата и время последнего редактирования в текущей сессии страницы. |

Справочник ответственных содержит 14 демонстрационных записей и использует wildcard-членство для всех проектов. Аватары хранятся как низкоразмерные photo-like face-only PNG `42×42px` с минимальным светлым фоном в `assets/images/assignees/` и отображаются только в интерфейсе выбора команды проекта. Реальные команды проектов, права назначения, постоянное хранение, backend, история статусов и изменений относятся к целевой модели.

## Сущность события

Событие описывает факт, риск, изменение, отсутствие ожидаемого факта или аналитический вывод, который отображается в ленте, детальной карточке и участвует в фильтрации.

Событие не является простой текстовой нотификацией. Это интеллектуально обработанный информационный блок, который переводит сырые сигналы со стройплощадки в понятный бизнес-контекст, показывает влияние на метрики и предлагает пользователю возможные действия.

## Источники появления событий

События появляются тремя способами:

| Источник | Как появляется событие |
| --- | --- |
| Внешние продукты | Событие поступает из подключенных систем, например S.Pass, Gantt или Control, как запись в базе данных или интеграционном контуре. |
| Система S.Center | Событие создается автоматически, если ожидаемый факт не наступил к плановой дате или не подтвердился данными. |
| ИИ-аналитика | Событие генерируется нейросетью на основе анализа массива событий, повторяющихся инцидентов или динамики за период. |

## Типы событий

| Тип события | Как формируется | Примеры |
| --- | --- | --- |
| Фактическое изменение | Поступает из внешних систем и продуктов. | Сдвиг сроков в графике, невыход рабочих, штраф подрядчику, замечание по безопасности, заявка на приемку работ. |
| Отсутствие ожидаемого факта | Формируется системой, если запланированное действие или контрольный этап не подтвердились к ожидаемой дате. В интерфейсе такая карточка визуально не должна отличаться от обычного события. | Плановая дата получения РНС наступила, но факт получения не зафиксирован. |
| Агрегированное аналитическое событие | Генерируется ИИ на основе группы однотипных или связанных событий, чтобы снизить информационную нагрузку пользователя. | Сводное событие о массовом сдвиге сроков по объекту или вывод о ненадежности подрядчика. |

Агрегированные события могут формироваться в двух режимах:

- ежедневная агрегация — объединяет мелкие однотипные инциденты, чтобы снизить информационный шум;
- периодическая агрегация — по итогам суток, недели или месяца формирует событие-вывод по проекту, очереди, подрядчику или другому аналитическому срезу.

## Приоритет события и отображение в ленте

Приоритет события определяется ИИ и влияет не на сущность события, а на способ его отображения и полноту карточки в ленте.

| Приоритет | Роль в интерфейсе | Правило карточки |
| --- | --- | --- |
| Высокий приоритет | Попадает в основной фокус пользователя и должен быстро привлекать внимание. | Карточка показывает расширенный краткий состав, включая связанную метрику и визуальную индикацию влияния на нее. |
| Низкий приоритет | Отделяется от основного фокуса, чтобы не перегружать информационное поле. | Карточка показывает суть события, но может не содержать блок влияния на метрику. В интерфейсе такие события могут быть вынесены в отдельный таб или сворачиваемую секцию. |

Различие приоритета не должно менять базовые атрибуты события: низкоприоритетное событие остается полноценной сущностью и может открываться в детальной карточке.

Критерии высокого приоритета:

- событие напрямую влияет на финансовую или строительную метрику;
- событие угрожает графику работ, например фиксирует массовый невыход рабочих или срыв ключевого этапа;
- событие связано со штрафами, замечаниями или повторяющимися нарушениями подрядчика;
- событие меняет даты ключевых этапов или нормативы строительства;
- событие является сводным аналитическим выводом ИИ за день, неделю или месяц и подсвечивает системную проблему.

Рутинные события, которые не влияют на сроки, бюджет или управленческий риск, например рядовая заявка на приемку работ, могут получать низкий приоритет и отделяться от основного фокуса.

Концептуальный атрибутивный состав события:

| Атрибут | Назначение |
| --- | --- |
| Наименование события | Короткий заголовок, который может генерироваться ИИ. |
| Источник события | Система или продукт, из которого поступили данные: S.Pass, Gantt, Control или несколько источников для агрегированного ИИ-события. |
| Адрес события | Точный контекст возникновения: проект, очередь, этап, тип объекта или конкретное здание. |
| Текст события | Развернутое описание ситуации, причин и контекста. |
| Влияние на метрику | Связь с нижней релевантной метрикой и прогнозное влияние на топ-метрику проекта, например прибыльность или чистую прибыль. Значение может выражаться в рублях или процентах. Одно событие может влиять на несколько метрик. |
| Действия по сути события | Управленческие шаги: создать задачу, запросить объяснения, связаться с подрядчиком или выполнить другое релевантное действие. |
| Действия с карточкой события | Системные функции управления: закрепить, удалить из выборки, изменить приоритет. |
| Приоритет события | Высокий или низкий статус, который используется ИИ для сортировки и управления выдачей. |
| Timestamp события | Точные дата и время фиксации события для таймлайна. |

Закрепленный атрибутивный состав:

| Атрибут | Назначение |
| --- | --- |
| `id` | Уникальный идентификатор события. |
| `type` | Тип сущности; для текущего слоя всегда `event`. |
| `priority` | Приоритет события: `high`, `critical`, `low`. |
| `sourceId` | Ссылка на источник события из каталога источников. |
| `sourceName` | Отображаемое имя источника. |
| `sourceIcon` | Иконка источника для карточек и drawer. |
| `sourceIds` | Массив источников события; используется для событий-агрегаторов. |
| `sources` | Нормализованный список источников с именем, иконкой и визуальной темой. |
| `sourceCount` | Количество источников, отображаемое в агрегированном индикаторе карточки. |
| `isSourceAggregator` | Признак события, собранного из нескольких источников. |
| `title` | Заголовок события. |
| `text` | Основное описание события. |
| `dateText` | Текстовое представление даты и времени. |
| `projectId` | Ссылка на проект, к которому относится событие. |
| `queueId` | Ссылка на очередь проекта. |
| `queue` | Отображаемое название очереди. |
| `objectType` | Тип объекта, например корпус. |
| `objectName` | Отображаемое имя объекта. |
| `metricId` | Ссылка на финансовую метрику, на которую влияет событие. |
| `metricName` | Отображаемое имя метрики. |
| `impact` | Текстовое значение влияния. |
| `impactValue` | Числовое значение прогнозируемого или визуального влияния события на связанную метрику. |

| `pinned` | Состояние закрепления события. |

## Представления события

Краткое представление используется карточкой в ленте. Обязательный состав карточки списка: источник, иконка источника, заголовок, дата и время, 2–3 строки описания, быстрые действия закрепления и исключения, состояние закрепления и состояние исключения.

Связанная метрика и визуальное влияние на нее обязательны для событий высокого приоритета. Для низкого приоритета этот блок может не отображаться, чтобы не перегружать ленту.

Расширенное представление используется детальной карточкой. Оно добавляет проект, очередь, тип объекта, объект, расширенное отображение источника, приоритета и связанной метрики.

Обязательный состав детальной карточки события:

| Блок | Какие данные содержит |
| --- | --- |
| Информационная шапка | Иконка или визуальная метафора события, заголовок события, источник, проект или другой адресный контекст, тег приоритета и timestamp при необходимости. |
| Ключевые параметры | Источник, время фиксации, адрес события: очередь, тип объекта, конкретный объект строительства или другой доступный уровень адреса. |
| Влияние на метрику | Название нижней релевантной финансовой или строительной метрики и прогнозное влияние на топ-метрику проекта. Если ML-расчет доступен, значение может отображаться в абсолютном выражении или процентах: красным при негативном отклонении и зеленым при позитивном. Если расчет отсутствует, блок скрывается или отображается без числового значения по текущим правилам интерфейса. |
| Описание и ИИ-аналитика | Подробное описание причин и последствий инцидента, а также акцентный блок `Вывод` с итоговым резюме ИИ. |
| Управленческие действия | Кнопки реакции на проблему: создать задачу, запросить обоснование, связаться с подрядчиком или другое релевантное действие. |
| Системные действия | Нижний тулбар управления карточкой: изменить приоритет, закрепить, удалить или исключить из выборки. |

## Адрес события и связь с иерархией

Адрес события — обязательный атрибут, который связывает событие со структурной иерархией системы.

Событие может быть привязано:

- к конкретному объекту строительства или этапу;
- к очереди строительства;
- к проекту в целом, если событие носит глобальный характер;
- к бизнес-юниту через родительский проект и очередь.

Если событие привязано к очереди, оно автоматически принадлежит родительскому проекту, а проект — своему бизнес-юниту. Эта наследуемая связь используется лентой событий, фильтрами, метриками и ИИ-аналитикой.

Правило выборки:

| Активный контекст | Какие события видны |
| --- | --- |
| Бизнес-юнит | События всех доступных проектов и очередей внутри бизнес-юнита. |
| Проект | События проекта и всех его очередей. |
| Очередь | Только события выбранной очереди и ее дочерних объектов или этапов. |

## Связь события с метриками

Связь события с метриками определяется ИИ или ML-моделью на основе дерева финансовых и строительных показателей.

Для события важно фиксировать два уровня влияния:

| Уровень влияния | Назначение |
| --- | --- |
| Прямое влияние на нижнюю метрику | Модель определяет самую низкоуровневую релевантную метрику, которую непосредственно затрагивает инцидент, например расходы на строительство, продажи или длительность работ. |
| Глобальное влияние на топ-метрику | Модель оценивает, как изменение на нижнем уровне по цепочке влияет на главную метрику проекта, например чистую прибыль. Влияние может выражаться в абсолютном денежном значении или в процентах. |

Одно событие может влиять на несколько метрик. Это особенно важно для агрегированных событий, которые ИИ формирует по итогам дня, недели или месяца: одно сводное событие может затрагивать несколько веток финансового или строительного дерева.

В текущем прототипе основная связь может храниться через `metricId` как первичная метрика события. Целевая модель должна допускать множественный список влияний, если событие затрагивает несколько показателей.

Пользовательский переход от события к метрике происходит через детальную карточку события. Акцентный блок `Влияние на метрику` показывает нижнюю релевантную метрику, определенную ИИ, и может показывать прогнозное влияние на топ-метрику проекта, если ML-расчет доступен. Визуальное значение влияния может быть скрыто правилами текущего прототипа, но данные связи должны оставаться в сущности события и использоваться аналитикой.

Для индивидуального события ИИ формирует описание причин и последствий, а также блок `Вывод`. Для массива событий ИИ анализирует очищенную выборку после фильтрации и ручных исключений. Для периодов система может создавать агрегированные аналитические события по итогам дня, недели или месяца.

## Исключение события из выдачи

Исключение события из выдачи — это управление информационным фокусом пользователя, а не удаление события из системы.

Правила исключения:

- событие не удаляется физически из базы данных или общего слоя данных;
- событие скрывается из текущей пользовательской выдачи;
- исключение помогает очистить выборку перед массовым ИИ-анализом;
- исключенные нерелевантные карточки не должны искажать вывод ИИ по подрядчику, периоду, проекту или другой аналитической выборке;
- исключение не влияет на числовые значения финансовых и строительных метрик;
- при возврате события оно снова может участвовать в ленте и аналитике в рамках текущих правил интерфейса.

Оба представления собираются из одной сущности события через функции слоя данных. Компоненты не должны хранить собственные копии этих значений.

## Сущность финансовой метрики

Финансовая метрика описывает показатель в древовидной структуре. Одна и та же структура используется правой панелью, drawer структуры метрик, фильтром и BI-графиком.

Ключевые финансовые метрики:

| Метрика | Роль в системе |
| --- | --- |
| Чистая прибыль | Северная звезда проекта и верхняя корневая метрика финансового дерева. |
| Валовая прибыль | Ключевая целевая метрика для руководителя проекта, потому что находится в зоне влияния РП. |
| Прибыль до налогообложения | Промежуточная родительская метрика между чистой прибылью и операционным результатом. |
| Операционная прибыль | Родительская метрика для валовой прибыли и операционных расходов. |
| Выручка | Доходная ветка, формирующая валовую прибыль. |
| Себестоимость | Расходная ветка, включающая строительство и землю. |

## Дерево финансовых метрик

Родительские финансовые метрики рассчитываются из дочерних с учетом математического признака: одни дочерние показатели прибавляются к родителю, другие вычитаются.

```text
Чистая прибыль
  + Прибыль до налогообложения
    + Прочие доходы
    + Операционная прибыль
      + Валовая прибыль
        + Выручка
          + Основная выручка
            + Выручка от квартир
            + Выручка от паркомест
          + Прочая выручка
        - Себестоимость
          - Строительство
          - Земля
      - Управленческие расходы
      - Коммерческие расходы
      - Прочие расходы
    - Финансовые расходы
  - Налог на прибыль
```

На нижнем уровне дерева находятся метрики-драйверы, например количество проданных метров, базовая стоимость квадратного метра и средний размер скидки. Они формируют значения нижних доходных метрик и через цепочку влияют на верхние показатели.

## Значения и расчет финансовых метрик

Для любой финансовой метрики базовыми значениями являются факт и план.

| Значение | Назначение |
| --- | --- |
| Факт | Текущее зафиксированное значение метрики на актуальный месяц. Обычно обновляется после закрытия финансового периода. |
| План | Бюджетное значение, заложенное в финансовую модель. |
| Прогноз | Ожидаемое финальное значение на момент окончания проекта с учетом текущих изменений. |
| Отклонение от плана | Разница между фактом и планом. |
| Отклонение от предыдущего месяца | Динамика показателя относительно прошлого периода. |

Родительская метрика рассчитывается математически из дочерних: доходные и положительные составляющие прибавляются, расходные, налоговые и отрицательные составляющие вычитаются.

Пример: `Чистая прибыль = Прибыль до налогообложения - Налог на прибыль`.

Пример: `Прибыль до налогообложения = Прочие доходы + Операционная прибыль - Финансовые расходы`.

## Влияние событий на прогноз метрик

События напрямую не должны переписывать текущий финансовый факт, потому что финансовый факт обычно фиксируется при закрытии месяца.

Событие формирует прогнозируемое влияние через ИИ и ML-модели:

1. ИИ определяет нижнюю релевантную метрику, на которую событие влияет напрямую, например количество проданных квартир, расходы на строительство или продажи.
2. ML-модель оценивает, как это локальное изменение пройдет по дереву метрик и повлияет на верхнюю метрику проекта, например чистую прибыль.

Результат такого расчета может отображаться в карточке события как прогнозируемое отклонение в рублях или процентах. Это влияние помогает пользователю понять риск, но не заменяет официальный финансовый факт.

Концептуальный атрибутивный состав финансовой метрики:

| Атрибут | Назначение |
| --- | --- |
| Наименование метрики | Отображаемое название показателя, например чистая прибыль, валовая прибыль или расходы. |
| Фактическое значение | Текущий показатель на актуальный месяц. |
| Плановое значение | Бюджетное значение, заложенное в план или финансовую модель. |
| Отклонение от плана | Разница между фактическим и плановым значением. |
| Отклонение от предыдущего месяца | Динамика метрики относительно прошлого месяца. |
| Прогнозное значение | Ожидаемое значение на момент окончания проекта с учетом текущих изменений. |
| Математический признак | Логический и визуальный индикатор влияния на итог: метрика прибавляется к результату или вычитается из него. |

Закрепленный атрибутивный состав:

| Атрибут | Назначение |
| --- | --- |
| `id` | Уникальный идентификатор метрики. |
| `name` | Отображаемое имя метрики. |
| `parentId` | Идентификатор родительской метрики; у корня `null`. |
| `fact` | Фактическое значение. |
| `plan` | Плановое значение. |
| `forecast` | Прогнозное значение. |
| `delta` | Отклонение. |
| `deltaPrevMonth` | Отклонение относительно предыдущего месяца. |
| `risk` | Признак риска. |
| `budgetImpact` | Направление влияния на бюджет: `+` или `-`. |
| `children` | Дочерние метрики. |

## Сущность строительного показателя

Строительные показатели описывают физическое и календарное состояние объекта, проекта или очереди. Они отображаются отдельно от финансового дерева метрик и делятся на две категории.

Ключевые строительные показатели:

| Показатель | Единица | Роль |
| --- | --- | --- |
| Длительность проекта | Дни | Показывает календарную длительность проекта или выбранного контекста. |
| Объем проекта или работ | Дни | Показывает объем планировочного или строительного цикла. |
| Общепродаваемая площадь | Квадратные метры | Главный ТЭП, отражающий физический масштаб объекта или очереди. |

### Метрики строительного цикла

К этой категории относятся показатели планировочного цикла, например длительность проекта в днях и объем работ в днях.

| Атрибут | Назначение |
| --- | --- |
| Тип или название | Определяет показатель: длительность, объем работ или другой строительный показатель. |
| Плановое значение | Бюджетное или плановое значение показателя. |
| Текущее значение | Фактическое или прогнозное значение на текущий момент. |

### Технико-экономические параметры

ТЭП описывают физические характеристики объекта или очереди, например общую продаваемую площадь.

| Атрибут | Назначение |
| --- | --- |
| Значение объема | Числовое значение параметра, например площадь в квадратных метрах. |
| Единица измерения | Единица параметра: квадратные метры, дни или другая применимая единица. |
| Стадия разрешительной документации | Статус параметра: до получения РНС, РНС получено, ЗОС или РВЭ получены. |

## Расчетное представление центрального дашборда метрик

`MetricsDashboardViewModel` не является новой промышленной сущностью. Это расчетное demo-представление выбранного проекта или очереди, которое собирает:

- `contextType`, `contextId`, `contextKey`, `projectId`, `queueId`, название контекста и бизнес-юнит;
- `updatedAt`, `dataStatus` и признак демонстрационных данных;
- `schedule`: даты старта и завершения, длительность, прогноз и отклонение;
- `milestones`: плановую, прогнозную или фактическую дату и статус контрольного этапа;
- `budgets`: основания `ЦП`, `ДУ`, `КС2` и два расчетных попарных сравнения для каждого основания;
- счетчики событий, связанных со сроками и бюджетными метриками.

В текущем этапе значения проекта устойчиво зависят от `projectId`, а значения очереди — от `queueId` и родительского `projectId`, но не являются результатом реальных Gantt, ERP или КС2-интеграций. Отсутствующий контекст нельзя заменять значениями последнего открытого проекта или очереди.

## Справочники и расчетные объекты

Не все сущности системы имеют одинаковую природу. Часть сущностей является справочниками, а часть формируется расчетом или агрегацией.

### Справочники

| Справочник | Назначение |
| --- | --- |
| Справочник кодов работ и событий | Методологический классификатор контрольных этапов и групп строительных работ, например получение РНС или монтажные работы. Используется для графиков, привязки событий и унификации названий. |
| Справочник действий | Преднастроенный набор управленческих реакций, например создать задачу, запросить объяснения, связаться с подрядчиком или открыть график. ИИ выбирает релевантные действия из этого набора. |

### Расчетные объекты

| Объект | Как формируется |
| --- | --- |
| Агрегированные показатели | Финансовые и строительные метрики рассчитываются по дереву метрик и по структурной иерархии: очередь → проект → бизнес-юнит. |
| ИИ-выводы | Генерируются на основе анализа одного события или массива событий, например по подрядчику, периоду, проекту или очереди. |
| Агрегированные события | Формируются системой автоматически по итогам периода, например недели или месяца, на основе посуточных изменений и связанных инцидентов. |

## Правила пересчета и прогнозного влияния

Целевая модель разделяет фактические значения метрик и прогнозное влияние событий. Факт и план финансовых метрик приходят из финансовой модели, учетных данных или закрытия периода. Операционное событие не должно напрямую переписывать текущий финансовый факт.

Финансовые метрики пересчитываются по дереву: родительская метрика складывается из дочерних с учетом математического признака, а также агрегируется по структурной иерархии `очередь → проект → бизнес-юнит`.

Событие влияет на прогноз, риск и аналитический вывод. ИИ определяет нижнюю релевантную метрику, ML-модель оценивает влияние на верхние показатели, а интерфейс показывает это влияние в карточке события как прогнозируемое отклонение в рублях или процентах.

Исключение события из выдачи не удаляет событие, не корректирует финансовый факт и не меняет числовые значения финансовых или строительных метрик. Оно убирает карточку из текущей пользовательской выборки и из текущего массива для ИИ-анализа. Если в прототипе `impactValue` используется для демонстрационного визуального пересчета при исключении или возврате события, это поведение должно считаться устаревшей технической аппроксимацией и не должно переноситься в целевую модель.

## Форматы отображения метрик

Одна и та же метрика может отображаться в интерфейсе в трех форматах. Форматы не создают разные сущности: они показывают разные представления одного расчетного дерева.

| Формат | Назначение | Правило отображения |
| --- | --- | --- |
| Правая панель | Основной статичный дашборд текущего контекста. | Показывает текущий месяц без длинных графиков: факт, план, отклонение от предыдущего месяца, закрепленные строительные показатели, выбранную фокусную финансовую метрику и один уровень ее дочерних метрик. |
| Drawer структуры метрик | Навигационное дерево всех показателей проекта. | Позволяет быстро выбрать любую метрику и перейти на нужный уровень. Показывает полную иерархию и визуальный математический признак влияния: показатель прибавляется к итоговой метрике или вычитается из нее. |
| BI-график | Детальный аналитический просмотр выбранной метрики. | Открывается в отдельной модалке по клику и показывает динамику на протяжении жизненного цикла проекта: исторические данные, линию бюджета и прогноз. |

## Параметры карточки метрики

Карточка финансовой или строительной метрики в правой панели является сводным цифровым показателем без длинного графика. Она показывает текущий отчетный срез, а не весь жизненный цикл проекта.

| Параметр | Назначение |
| --- | --- |
| Название метрики | Имя показателя, например `Чистая прибыль`, `Длительность проекта` или `Объем проекта`. |
| Фактическое или текущее значение | Актуальная цифра на текущий отчетный месяц. |
| Плановое значение | Бюджетное или плановое значение. |
| Прогнозное значение | Ожидаемая финальная цифра на момент окончания проекта или периода. |
| Отклонение | Разница между фактом и бюджетом, а также динамика относительно предыдущего месяца. |
| Визуальная иконка | Быстрая ассоциация с типом показателя, например календарь для длительности или куб для объема. |

## Параметры строк деревьев

В системе есть два разных типа навигационных деревьев.

| Дерево | Назначение строки | Параметры |
| --- | --- | --- |
| Дерево структуры метрик | Навигация по финансовой иерархии. | Название показателя, математический индикатор `+` или `-`, уровень вложенности, состояние выбора и раскрытия. |
| Структурное дерево объектов | Выбор базового контекста и первичная фильтрация данных. | Для бизнес-юнита: название, общая картинка, руководитель. Для проекта: название, фотография, стадия строительства, кластер, регион, РП. Для очереди: номер или название, ТЭП, общая продаваемая площадь, стадия разрешительной документации. |

## Компоненты-потребители

| Область интерфейса | Какие данные использует |
| --- | --- |
| Лента событий | Краткое представление события. |
| Детальная карточка события | Расширенное представление события. |
| Фильтр | Каталог источников, приоритеты и дерево метрик. |
| Расчетные связи метрик | `metricId`, `metricName`, активная метрика и дерево метрик для карточек событий, фильтров и ассистента. |
| BI-график | Активный `src/features/bi/` получает выбранный узел из `window.metricsData`; месячная история пока демонстрационная. |
| Правая панель и структура метрик | Изолированы в `legacy/isolated/right-metrics-panel/` и не являются активными потребителями. |

## Текущее состояние прототипа и целевая модель

| Область | Уже отражено в прототипе | Целевая модель / будущий этап |
| --- | --- | --- |
| Бизнес-юниты, проекты и очереди | Есть демонстрационное дерево в `src/data/project-structure.js`; выбор узла меняет активный контекст. | Реальные права видимости, руководители, этапы, объекты строительства и более глубокая адресация событий. |
| События | Есть единый массив событий с `businessUnitId`, `projectId`, `queueId`, источником, приоритетом, текстом, метрикой и состояниями `pinned`/`excluded`. | Реальные события из S.Pass, Gantt, Control; события отсутствия ожидаемых фактов; периодические аналитические события; множественное влияние на метрики. |
| Финансовые метрики | Есть демонстрационное дерево и расчетные значения по активному контексту; правый визуальный блок изолирован. | Реальный источник факта, плана, прогноза, предыдущего месяца, отдельный источник арифметики дерева и решение о будущем визуальном представлении. |
| BI-график | Открывается из детальной карточки события, использует выбранную метрику текущего контекста и позволяет включить демонстрационный прогноз. | Реальная история по жизненному циклу проекта, единицы измерения, бюджетная линия и промышленная методика прогноза. |
| Строительные показатели | Есть контекстные расчетные данные длительности и объема; визуальные карточки правой панели изолированы. | Полноценные ТЭП, общепродаваемая площадь, стадии РНС/ЗОС/РВЭ и расширенный набор строительных показателей. |
| AI-выводы | Есть демонстрационные тексты и сценарий запуска анализа по текущей выборке. | Реальная AI/ML-модель, индивидуальный анализ, массовый анализ, рекомендации и периодические выводы. |
| Цифровая шахматка | Есть demo-сущности объекта строительства, периода, работы и ячейки готовности; доступны 5 объектов, 27 работ, календарь и сравнение двух матриц. Ячейки детерминированно имитируют неравномерный фронт работ, разные темпы секций и локальные отклонения без объявления этой генерации бизнес-методикой. | Реальные справочники работ и объектов, методика расчета факта/плана, интеграционные источники, права и persistence. |
| Сводка цифровой шахматки | Есть контекстное demo-представление проекта: KPI, недельная динамика, проблемы, строки пяти объектов и архивные снимки; это производный view-model поверх Project/ConstructionObject, а не новая сущность. | Реальные источники KPI и рисков, методика агрегации, серверный архив, права, persistence и согласованные cross-feature переходы. |
| Объекты | Есть общий каталог стабильной идентичности пяти объектов и отдельная project-view-model с паспортом, 32 `WorkGroup` и 15–27 `WorkType` в каждой группе; `queue` наследует проект, business unit не получает проектные строки. | Согласовать единую геометрию объекта, `LegalEntity`, справочник работ, действия строки, реальную методику готовности, источники, права и persistence. |
| Действия пользователя | Создание, редактирование и удаление задачи из события работают в памяти страницы; карточка задачи и индикатор связи синхронизированы с событием. Остальные действия остаются визуальными. | Постоянное хранение, реальная интеграция с трекером задач, workflow статусов, история, права, запросы объяснений, коммуникации и график работ. |
| Роли и доступы | Описаны в документации. | Реальная адаптация интерфейса, дерева, метрик, событий и действий под роль пользователя. |

Эта таблица связана с `docs/system-compliance-matrix.md`: если сущность переходит из целевой модели в реализацию прототипа, нужно обновить оба документа.

## Ограничения этапа

Структурные сущности и информационные сущности описаны как целевая модель предметной области. Подробный атрибутивный состав уже закреплен для событий и финансовых метрик; атрибуты бизнес-юнита, проекта, очереди, этапа, объекта строительства, ТЭП, ИИ-вывода и действия должны уточняться отдельными итерациями по мере развития данных и интерфейса.

Поврежденная русская кодировка старых интерфейсных текстов не восстанавливается в этом этапе.

Публичные глобальные интерфейсы `window.*` сохраняются, чтобы не ломать уже подключенные компоненты.
