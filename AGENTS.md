# AGENTS.md

## Назначение

Краткая обязательная инструкция для AI-агентов проекта S.Center. Подробные продуктовые, архитектурные и документационные сведения находятся в профильных источниках и не дублируются здесь.

S.Center — прототип личного кабинета для централизации проектной информации, выявления событий и инцидентов, анализа метрик и поддержки управленческих решений. Главный пользовательский фокус — работа с событиями; метрики и AI-аналитика поддерживают этот сценарий.

## Обязательные правила

- Документацию писать на русском языке; технические имена файлов, функций, классов, CSS-селекторов и `window.*` оставлять в оригинальном виде.
- Не менять код прототипа, если задача документационная и пользователь отдельно не запросил изменение кода.
- Не смешивать текущую реализацию, целевую модель, переходный план и историю.
- Не выдавать демонстрационные данные и расчеты за промышленную модель.
- При расхождении прототипа с продуктовой моделью сначала фиксировать расхождение в документации.
- Изменение назначения, данных, состояния, визуального слоя, публичного интерфейса или пользовательского пути сопровождать обновлением связанных документов в том же этапе.
- Не изменять файлы вне области задачи и сохранять пользовательские изменения в рабочем дереве.

## Рабочий порядок

Применять последовательность: контекст → декомпозиция → исполнение → проверка связей → документация → приемка.

Перед изменением:

1. Определить тип и границы задачи.
2. Определить уровень сложности по `docs/plans/README.md`.
3. Открыть быстрый маршрут `docs/README.md` и найти строку реестра затронутого владельца; не загружать остальные группы документов без конкретной причины.
4. Проверить только относящиеся к задаче строки или разделы `docs/component-map.md`, `docs/component-impact-map.md` и `docs/system-compliance-matrix.md`. Полное чтение этих документов требуется только для межсистемной задачи или аудита.
5. Определить, относится требование к текущему прототипу или будущей модели.
6. Перед поиском по репозиторию прочитать `.agentsignore` и самостоятельно исключить перечисленные области.

Контекст расширяется только ради конкретного недостающего факта. Архив, evidence, reference, завершенные аудиты и изолированные области не входят в минимальный пакет локальной реализации.

После изменения:

1. Проверить затронутые пользовательские сценарии.
2. Обновить README компонента, feature или слоя, если изменился его контракт.
3. Обновить `docs/system-compliance-matrix.md`, если изменились статус, данные, визуальный слой или пользовательский путь.
4. Обновить `docs/component-impact-map.md`, если изменилась связность.
5. Обновить `docs/plans/system-scaling-roadmap.md`, если выявлено будущее требование.
6. Если создан, перемещен, архивирован или удален документ, обновить `docs/README.md`.
7. После изменения документации выполнить `node scripts/check-documentation.mjs`; ошибка checker блокирует приемку.

## Источники истины

| Область | Основной источник |
| --- | --- |
| Навигация и статус документации | `docs/README.md` |
| Общие правила проекта | `PROJECT_GUIDELINES.md` |
| Классификация и жизненный цикл документов | `docs/documentation-standards.md` |
| Текущая реализация и расхождения | `docs/system-compliance-matrix.md` |
| Топология и каскадное влияние | `docs/component-map.md`, `docs/component-impact-map.md` |
| Сущности и данные | `docs/entity-model.md`, `src/data/README.md` |
| Связующий слой приложения | `src/app/README.md` |
| Компонент или пользовательский сценарий | README соответствующего каталога `src/components/` или `src/features/` |
| Планирование и будущая модель | `docs/plans/README.md`, `docs/plans/system-scaling-roadmap.md` |

Текущий прототип описывается локальными README, `docs/component-map.md` и `docs/system-compliance-matrix.md`. Будущая реализация описывается roadmap и профильными планами. Целевые сущности в `docs/entity-model.md` должны быть явно отделены от демонстрационных данных.

## Границы структуры

Не считать перечень каталогов в этой инструкции окончательной архитектурой. Актуальная маршрутизация находится в `docs/README.md` и `docs/component-map.md`.

`legacy/isolated/` не входит в активный прототип. Не читать, не индексировать и не использовать его при обычной работе, даже если общий поиск находит эти файлы. Открывать конкретный изолированный модуль можно только по прямой команде пользователя на восстановление, аудит или повторную интеграцию.

`.agentsignore` — проектное соглашение, а не автоматически исполняемый механизм Codex. Агент обязан применять его правила самостоятельно при поиске и обзоре структуры.

## Компоненты, данные и `src/app`

- Компонент отвечает за отображение и локальное поведение; крупный пользовательский сценарий документируется как feature.
- Компоненты и features не создают копии сущностей, если они уже существуют в `src/data/`.
- Демонстрационные, расчетные, будущие справочные и будущие интеграционные данные различаются явно.
- `src/app` связывает контекст, данные и перерисовку интерфейса, но не становится самостоятельным источником сущностей.
- Изменение публичных `window.*` требует отдельного осознанного этапа и синхронизации документации.

## Субагенты

Субагентов подключать только к независимым ограниченным задачам, когда это прямо запрошено пользователем или предусмотрено утвержденным планом.

Основной агент:

- задает субагенту узкую область ответственности и передает только релевантный контекст;
- не поручает неограниченное изменение архитектуры;
- проверяет результат по проектным правилам, карте влияния и матрице соответствия;
- объединяет результаты и сохраняет ответственность за итоговое качество;
- не допускает параллельного редактирования пересекающихся файлов без координации.

Субагент не принимает финальные архитектурные решения. Изменение данных, пользовательского пути, визуального слоя, публичного интерфейса или статуса соответствия принимается и документируется основным агентом.

## Проверка и приемка

Если менялся код:

- проверить синтаксис измененных JS-файлов;
- проверить локальные подключения из `index.html`;
- проверить затронутые пользовательские сценарии в интерфейсе.

Если менялась только документация:

- проверить внутренние связи и статус документа в `docs/README.md`;
- проверить разделение текущей и будущей модели;
- подтвердить отсутствие изменений JS, CSS и HTML.

Работа завершена, если прямое требование выполнено, связанные документы синхронизированы, результаты субагентов проверены, расхождения имеют следующее действие, а несвязанные файлы не изменены.

## Запреты

- Не удалять функциональность без явной команды пользователя.
- Не менять публичные `window.*` без отдельного этапа.
- Не восстанавливать изолированные модули без прямой команды.
- Не выполнять массовое исправление поврежденной кодировки вместе с другой задачей.
- Не переводить проект на ES-модули, сборщик или новую технологию без отдельного решения.
- Не реализовывать future-требования автоматически, если пользователь запросил только документацию или аналитику.
