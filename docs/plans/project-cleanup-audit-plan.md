# План: комплексный аудит структуры и чистки проекта

Тип: `макроплан`
Статус: `этапы 0–4 выполнены; ожидается пользовательский gate`
Временной слой: `переходное состояние`
Основной источник: `docs/README.md`
Связанный план: `docs/plans/documentation-cleanup-plan.md`
Условие закрытия: весь активный проект проверен, каждое предложение подтверждено зависимостями и ценностью, согласованные действия выполнены отдельными обратимыми пакетами, документация синхронизирована.

## Goal

Провести полный контролируемый аудит S.Center и подготовить доказательный перечень:

- активных и необходимых файлов и каталогов;
- пустых, сгенерированных, временных и нефункциональных каталогов;
- неиспользуемых файлов, ресурсов и интеграционных пакетов;
- лишней, устаревшей и дублирующей документации;
- смысловых блоков документов, не имеющих функциональной, управленческой, доказательной или исторической ценности;
- безопасных действий: оставить, уточнить, объединить, переместить, архивировать или удалить.

Сам аудит не является разрешением на удаление. Фактическая чистка выполняется только после модерации основным агентом и подтверждения конкретного пакета изменений пользователем.

## Context

Предварительная нейтральная карта, собранная без чтения `legacy/isolated/`, содержит 102 каталога и 368 файлов вне `.git`, каталогов зависимостей и исключенной области.

Области повышенного внимания:

| Область | Предварительный признак | Что требуется доказать |
| --- | --- | --- |
| `.agents/` | каталог пуст | Нужен ли он для ближайшего project skill или может отсутствовать до фактического создания skill. |
| `.vite/` | два небольших cache-файла | Является ли каталог полностью воспроизводимым и должен ли игнорироваться Git. |
| `.backups/` | 99 файлов, около 7 МБ | Есть ли уникальные точки восстановления и установленный срок хранения. |
| `output/` | 87 файлов, около 57 МБ | Какие артефакты являются принятым evidence, а какие воспроизводимым промежуточным выводом. |
| `design-audit/` | 17 файлов, около 6,8 МБ | Какие результаты подтверждают активные UI-контракты и куда их маршрутизировать. |
| `qa/` | 10 файлов, около 4,1 МБ | Какие снимки являются действующими regression/evidence. |
| `chat-transfer-package/` | переносимый пакет рядом с активным feature чата | Остались ли runtime-зависимости и уникальные API/UX-контракты. |
| `docs/plans/` | содержит активные и завершенные планы | Какие планы должны оставаться активными, а какие перейти в архив. |
| корень проекта | `.gitignore` отсутствует | Какие воспроизводимые каталоги и файлы должны быть исключены из контроля версий. |

Эти признаки не являются выводами об удалении и повторно проверяются на этапе исполнения.

## Критерии ценности

Элемент сохраняется, если имеет хотя бы один подтвержденный вид ценности:

| Вид ценности | Примеры |
| --- | --- |
| Runtime | Подключен из `index.html`, вызывается кодом, участвует в данных, UI или пользовательском пути. |
| Операционная | Нужен для запуска, проверки, сборки, агентской работы или воспроизводимости окружения. |
| Нормативная | Является основным или дополняющим источником требований и контрактов. |
| Управленческая | Фиксирует принятое решение, ограничение, владельца или следующее действие. |
| Доказательная | Подтверждает приемку, regression, визуальное решение или происхождение требования. |
| Историческая | Нужен для объяснения значимого решения и корректно находится в архиве. |

Отсутствие прямого вызова в коде не означает отсутствие ценности. Reference, планы, evidence и архив оцениваются по своим критериям.

## Scope

В аудит входят:

- корневые файлы и каталоги проекта;
- `index.html`, `src/`, `assets/`, `scripts/`;
- корневая и локальная документация;
- `docs/`, включая plans, reference и archive;
- `.agents/`, `.vite/`, `.backups/`;
- `qa/`, `output/`, `design-audit/`;
- `chat-transfer-package/`;
- пустые каталоги;
- дубли, orphan-файлы, неиспользуемые assets и несвязанные документы;
- правила исключения воспроизводимых файлов из Git.

## Out of Scope

- чтение и аудит `legacy/isolated/` без отдельной прямой команды пользователя;
- удаление или изменение активной функциональности в ходе исследовательской волны;
- архитектурный рефакторинг, переход на ES-модули, сборщик или новую технологию;
- исправление продукта, обнаруженное во время аудита, если оно не требуется для проверки кандидата на чистку;
- массовая правка кодировки старых файлов;
- автоматическое удаление элемента только потому, что он пуст, старый или не найден текстовым поиском.

## Состав команды

Используются три субагента и один основной агент. Это максимальная полезная параллельность для текущих четырех рабочих слотов без дробления ответственности и параллельного редактирования одних файлов.

### Субагент 1 — runtime и зависимости

Область: `index.html`, `src/`, `assets/`, `scripts/`, публичные `window.*` и связи активного интерфейса.

Задачи:

- построить граф подключений и фактических потребителей;
- найти orphan JS/CSS/assets, дубли реализаций и неиспользуемые точки входа;
- отличить динамический вызов от действительно отсутствующей зависимости;
- отметить риск удаления для пользовательских сценариев;
- не менять файлы.

Результат: таблица находок `RT-*` с доказательствами входящих и исходящих связей, риском и рекомендуемой проверкой.

### Субагент 2 — документация и смысловая ценность

Область: корневые Markdown/TXT, `docs/`, README внутри `src/`.

Задачи:

- проверить источники истины, ссылки, статусы и временные слои;
- найти полные и частичные смысловые дубли;
- выявить устаревшие, бессрочные и немаршрутизированные документы;
- проверить лишние разделы внутри документов по критериям ценности;
- использовать `docs/plans/documentation-cleanup-plan.md` как дочерний план;
- не менять файлы.

Результат: таблица находок `DOC-*` с точным документом и разделом, владельцем смысла, уникальным содержанием и предлагаемым действием.

### Субагент 3 — вспомогательные каталоги и evidence

Область: `.agents/`, `.vite/`, `.backups/`, `qa/`, `output/`, `design-audit/`, `chat-transfer-package/`, пустые каталоги и правила Git-исключений.

Задачи:

- разделить source, cache, backup, generated output, reference и evidence;
- определить воспроизводимость и стоимость повторного создания;
- проверить входящие ссылки из активного проекта и документации;
- предложить политику хранения, архивирования и `.gitignore`;
- не менять и не удалять файлы.

Результат: таблица находок `ART-*` с объемом, типом артефакта, воспроизводимостью, входящими ссылками и рекомендуемой политикой хранения.

### Основной агент — модератор и владелец решения

Основной агент:

- фиксирует границы и выдает каждому субагенту непересекающийся пакет;
- ведет единый реестр находок и не позволяет субагентам редактировать его параллельно;
- проверяет все рекомендации на соответствие `docs/component-impact-map.md` и `docs/system-compliance-matrix.md`;
- разрешает пересечения между runtime, документацией и evidence;
- запрашивает повторную read-only проверку спорных кандидатов у другого субагента;
- определяет итоговый класс элемента, но не удаляет его без пользовательского gate;
- выполняет или координирует согласованные изменения пакетами;
- отвечает за итоговую регрессию и синхронизацию документации.

## Единый формат находки

Каждый результат субагента должен содержать:

| Поле | Содержание |
| --- | --- |
| ID | `RT-*`, `DOC-*` или `ART-*`. |
| Путь и граница | Точный файл, каталог или диапазон раздела документа. |
| Текущий класс | active source, operational, normative, reference, evidence, archive, generated, cache, backup, unknown. |
| Доказательства | Подключения, ссылки, потребители, уникальный смысл, история или воспроизводимость. |
| Риск | Низкий, средний, высокий или защищенный. |
| Предложение | Оставить, уточнить, объединить, переместить, архивировать, удалить или дополнительно проверить. |
| Условие действия | Что должно быть подтверждено до изменения. |
| Связанные документы | Карта, матрица, README, план или reference для синхронизации. |

Формулировка «не используется» без доказательств не принимается основным агентом.

## Правила модерации и синхронизации

1. Первая волна полностью read-only; субагенты не создают, не редактируют, не перемещают и не удаляют файлы.
2. Основной агент перед стартом фиксирует общий снимок `git status`, исключения и состав областей.
3. Один путь имеет одного первичного владельца. Пересечение фиксируется ссылкой на finding другого агента, а не дублирующей рекомендацией.
4. Все находки передаются основному агенту в едином формате; только он создает канонический отчет.
5. Кандидат со средним или высоким риском получает независимую вторую проверку агентом из другой области.
6. При конфликте выводов приоритет имеют фактическая runtime-зависимость, основной источник истины и более сильное доказательство, а не большинство голосов.
7. Неясный элемент получает статус `требует решения`, а не автоматически `удалить`.
8. Субагент не меняет архитектурный, продуктовый или compliance-статус элемента.
9. Между волнами основной агент публикует нормализованный список подтвержденных, спорных и отклоненных находок.
10. Параллельные записи в одни файлы запрещены; изменения выполняются последовательно по пакетам.

## Этапы выполнения

### Этап 0 — baseline и защита границ

- зафиксировать `git status`, перечень tracked/untracked файлов и объемы каталогов;
- подтвердить исключение `.git`, зависимостей и `legacy/isolated/`;
- определить временные файлы аудита и не включать их в постоянную документацию без необходимости;
- создать единый канонический отчет аудита.

### Этап 1 — параллельная первичная проверка

- запустить трех субагентов по указанным областям;
- основной агент параллельно проверяет полноту покрытия и существующие карты;
- дождаться всех трех отчетов до формирования выводов.

### Этап 2 — нормализация и устранение пересечений

- объединить находки в общий реестр;
- удалить дубли finding, но сохранить независимые доказательства;
- назначить класс ценности, риск и владельца решения;
- выделить спорные элементы для второй проверки.

### Этап 3 — перекрестная проверка

- runtime-кандидаты проверяются на документационные и evidence-ссылки;
- документационные кандидаты проверяются на уникальные контракты и историю решений;
- generated/evidence-кандидаты проверяются на невоспроизводимые материалы;
- для каждого кандидата на удаление подтверждается отсутствие скрытой или динамической зависимости.

### Этап 4 — формирование пакетов действий

Находки группируются в независимые пакеты:

1. Пустые каталоги и воспроизводимые cache-файлы.
2. Backup и generated output с политикой хранения.
3. Evidence, QA и визуальные reference.
4. Документация и лишние смысловые блоки.
5. Завершенные планы и архив.
6. Переносимый пакет чата.
7. Неиспользуемые runtime-файлы и assets.
8. Правила `.gitignore` и предотвращение повторного накопления.

Для каждого пакета указываются точные пути, ожидаемый эффект, способ восстановления, проверки и документы для обновления.

### Этап 5 — пользовательский gate

До удаления, необратимого перемещения или сокращения уникального содержания основной агент представляет пользователю:

- список точных целей;
- основание и доказательства;
- риск и каскадное влияние;
- что будет сохранено или перенесено;
- способ восстановления;
- проверки после действия.

Без подтверждения допускаются только исправления самого плана и read-only аудит.

### Этап 6 — последовательная чистка

- выполнять по одному согласованному пакету;
- перед каждым пакетом повторно проверять точные пути;
- сначала переносить уникальное знание, затем удалять замененный источник;
- после каждого пакета выполнять локальные проверки и проверять `git diff`;
- не смешивать документальную чистку с функциональным рефакторингом.

### Этап 7 — финальная приемка

- проверить запуск и основные пользовательские сценарии, если менялись runtime-файлы;
- проверить локальные подключения, публичные `window.*`, assets и синтаксис JS;
- проверить все внутренние документационные ссылки и реестр `docs/README.md`;
- обновить component map, impact map и compliance matrix при фактическом изменении структуры;
- подтвердить отсутствие согласованных кандидатов без решения;
- зафиксировать новую политику хранения и предотвращения повторного накопления.

## Проверка смысловых блоков документации

Раздел документа является кандидатом на сокращение только если одновременно выполнены условия:

- содержание полностью воспроизводится из более авторитетного актуального источника;
- раздел не содержит уникального решения, ограничения, причины или критерия приемки;
- на раздел не опирается активный план, сценарий или evidence;
- удаление не смешивает текущую и будущую модель;
- после удаления сохраняется понятный маршрут к владельцу смысла.

Длинный, исторический или нефункциональный раздел сам по себе не считается лишним. При наличии исторической ценности он переносится в архив; при наличии доказательной ценности — в evidence; при наличии будущего требования — в roadmap или активный план.

## Риски

| Риск | Мера контроля |
| --- | --- |
| Динамические зависимости не находятся текстовым поиском | Проверять `index.html`, `window.*`, DOM-id, CSS-селекторы и пользовательский сценарий. |
| Evidence ошибочно принимается за мусор | Проверять связь с приемкой и невозможность повторного получения. |
| Backup удаляется без точки восстановления | Определять срок хранения и альтернативный источник в Git до удаления. |
| Документ сокращается с потерей решения | Сначала переносить уникальное содержание и только затем удалять дубль. |
| Субагенты дают противоречивые рекомендации | Основной агент выполняет перекрестную проверку и фиксирует решение с доказательством. |
| Параллельная работа создает конфликт | Субагенты работают read-only, запись выполняет основной агент последовательно. |
| Чистка превращается в рефакторинг | Любое функциональное изменение выносится в отдельный план. |

## Acceptance Criteria

План аудита считается выполненным, когда:

- все разрешенные области проекта покрыты одним из владельцев;
- каждый найденный элемент имеет доказательный статус и следующее действие;
- все кандидаты на удаление прошли проверку ссылок, зависимостей и уникальности;
- спорные кандидаты получили независимую вторую проверку;
- пользователь утвердил конкретные пакеты необратимых действий;
- согласованные пакеты выполнены и проверены отдельно;
- активный прототип сохранил пользовательские сценарии;
- документация, карты, матрица и реестр отражают итоговую структуру;
- `legacy/isolated/` не читался и не изменялся без прямой команды.

## Verification

- сравнить списки файлов до и после каждого пакета;
- проверить отсутствие неожиданных изменений вне пакета;
- проверить битые Markdown-ссылки и зарегистрированность документов;
- проверить `index.html` и существование локальных подключений;
- выполнить syntax-check измененных JS-файлов;
- выполнить browser-проверку затронутых сценариев при runtime-чистке;
- проверить отсутствие изменений внутри `legacy/isolated/`;
- сохранить итоговый отчет с принятыми, отклоненными и отложенными находками.
