# Слой данных

## Назначение

`src/data/` хранит единые источники данных и расчетные функции. Компоненты не должны создавать собственные копии событий, метрик, проектов или очередей.

После изоляции правого блока метрик данные метрик остаются активными, потому что используются карточками событий, фильтрами, ассистентом и восстановленным BI-графиком. Визуальная правая панель и drawer структуры метрик остаются в `legacy/isolated/right-metrics-panel/`; самостоятельный `src/features/bi/` использует выбранный узел текущего `window.metricsData`.

Помесячная серия BI-графика генерируется внутри feature детерминированно для проверки интерфейса. Она не добавляет новую сущность в `src/data`, не меняет `fact`, `plan` или `forecast` и не считается промышленной историей метрики.

| `metrics-dashboard-data.js` | Контекстные demo-данные центрального дашборда для проекта и очереди: сроки, контрольные этапы, бюджетные основания и расчет согласованных отклонений. |

| `construction-objects-data.js` | Единый каталог стабильной идентичности пяти объектов: `id`, название, тип, подпись типа и иконка. |

## Публичные интерфейсы

`window.appData` предоставляет:

- `getEventsForContext(context)`;
- `getMetricsForContext(context, events)`;
- `getConstructionMetricsForContext(context)`;
- `getEventSources()`;
- `getPriorities()`;
- `getMetricSelectorTree(metricsRoot)`;
- `getEventListViewModel(event, metricsRoot)`;
- `getEventDetailViewModel(event, metricsRoot)`;
- `findMetricById(node, id)`;
- `findMetricPathById(node, id)`.

`window.metricsDashboardData` предоставляет:

- `getDashboardForContext(context, events)`;
- `differenceInDays(startDate, endDate)`;
- `buildComparison(value, baseValue, baseCode)`.

В демонстрационных бюджетных основаниях поле `name` содержит полную расшифровку из визуального референса. Перенос строки внутри значения используется только для устойчивого двухстрочного отображения дескрипшна карточки и не меняет смысл или схему данных.

Для `Nova` на уровне проекта используются значения бюджетных оснований из референса; для каждого основания вычисляются два попарных сравнения с остальными основаниями. Прогнозная дата вычисляется как плановая дата плюс отклонение. Для остальных проектов значения устойчиво зависят от `projectId`. Для очередей значения устойчиво зависят от `queueId` и родительского `projectId`, а `MetricsDashboardViewModel` получает отдельный `contextKey`, чтобы переключение между очередями одного проекта не оставляло stale-данные предыдущего проекта или очереди. Это демонстрационная модель, а не интеграционный источник.

`window.projectStructureData` предоставляет:

- `getProjectStructure()`;
- `findProjectEntityById(id)`;
- `getContextScope(type, id)`.

`window.taskData` предоставляет:

- `getAssigneesForProject(projectId)`;
- `getAssigneeById(id)`;
- `getTasksForEvent(eventId)`;
- `getTaskById(taskId)`;
- `getTaskCountForEvent(eventId)`;
- `createTask(input)`;
- `updateTask(taskId, input)`;
- `deleteTask(taskId)`.

`window.digitalChessboardData` предоставляет:

- `getForContext(context)` — проектный demo-набор; для очереди используется родительский `projectId`, для бизнес-юнита возвращается `unsupported-context`;
- `validate(model)` — проверка демонстрационного состава и наличия всех пяти статусов в совокупной матрице каждого объекта и периода;
- `STATUS` — `in-progress`, `completed`, `delayed`, `no-data`, `not-applicable`.

Ячейки шахматки формируются устойчиво для одного и того же контекста, но не повторяют линейную «лесенку»: у каждой работы и секции есть собственный фронт выполнения, темп и локальные отклонения. Проценты используют сочетание целых значений и шага `5%`, завершённые зоны содержат как `100%`, так и значения `95–99%`; отставание, отсутствие данных и неприменимость распределяются разреженно. Среднее по применимым ячейкам остаётся близким к общей готовности работы. Это демонстрационная правдоподобная раскладка, а не промышленная методика расчёта.

`window.constructionObjectsData` предоставляет `getAll()`, `getById(objectId)` и `validate()`. Каталог намеренно не объединяет паспортные параметры раздела `Объекты` с геометрией матрицы шахматки.

`window.digitalChessboardSummaryData` предоставляет `getForContext(context)`, `validate(model)` и `STATUS`. Проект возвращает собственную детерминированную сводку, очередь наследует `projectId`, а business unit получает явный `unsupported-context`. KPI, риски, недельные выводы и архив остаются демонстрационным view-model и не объявляются промышленной методикой.

Сводка не хранит отдельный каталог проектов и не переносит числовые фикстуры бывшего локального стенда как бизнес-истину. Project identity поступает из `projectStructureData`, identity объектов — из `constructionObjectsData`, готовность — из project-view-model `objectsData`; остальные значения устойчиво формируются для проверки интерфейса. Реальные формулы KPI и рисков, источник недельных событий, серверный архив, права и persistence остаются будущим этапом. Stand-only API `window.DigitalChessboardSummaryData` и диагностический `window.digitalChessboardSummaryStand` не являются контрактами основного прототипа.

`window.objectsData` предоставляет:

- `getForContext(context)` — для `project` и `queue` возвращает проектную модель, для business unit — `unsupported-context` без stale-данных;
- `validate(model)` — проверяет 5 объектов, 32 группы на объект, 15–27 дочерних работ и обязательные атрибуты;
- `STATUS` — статусы строк таблицы раздела `Объекты`.

Методы чтения возвращают копии данных. `createTask()` и `updateTask()` проверяют обязательные название, описание и ответственного. `deleteTask()` удаляет задачу только из in-memory массива текущей страницы. Задачи хранятся отдельно от пересоздаваемого при смене контекста массива событий и сохраняются только до перезагрузки страницы.

## Сущности

Основные сущности слоя:

- событие;
- объект строительства с общей идентичностью; отдельно — период шахматки, работа и ячейка матрицы, а также паспорт объекта, группа и вид работ раздела `Объекты`;
- задача;
- ответственный;
- финансовая метрика;
- строительный показатель;
- бизнес-юнит;
- проект;
- очередь;
- активный контекст.

## Типы данных в прототипе

| Тип данных | Что входит сейчас | Правило развития |
| --- | --- | --- |
| Демонстрационные данные | События, задачи текущей страницы, 14 ответственных, источники, приоритеты, дерево финансовых метрик, строительные показатели, проектный дашборд, общий каталог объектов, feature-specific данные шахматки и раздела `Объекты`, бизнес-юниты, проекты и очереди. | Можно расширять для проверки интерфейса, но нельзя считать реальным промышленным источником. |
| Расчетные данные | Контекстные финансовые и строительные показатели, счетчики событий, краткое и расширенное представление события, дерево метрик для интерфейса. | Должны строиться из одного источника и не дублироваться локально в компонентах. |
| Будущие справочники | Роли, права доступа, справочник действий, справочник кодов работ и событий, источники интеграций, правила арифметики дерева метрик. | Должны быть вынесены отдельно до подключения реальных данных и AI/ML-логики. |
| Будущие интеграционные данные | События из S.Pass, Gantt, Control и других внешних систем. | Должны проходить нормализацию перед попаданием в единую модель события. |

Разделение типов данных связано с `docs/system-compliance-matrix.md`: если демонстрационная сущность становится целевой реализацией или появляется новый будущий справочник, нужно обновить матрицу и `docs/entity-model.md`.

## Тексты событий

`app-data.js` формирует для каждого события два текстовых представления. Оба текста имитируют результат AI-аналитики и агрегирования источников: они должны быть структурированными, с пунктами, абзацами, акцентами и числовыми параметрами, а не просто повествовательными описаниями.

- `title` / `listTitle` — нормализованное смысловое наименование события для компактной и детальной карточки. Заголовок не должен перечислять проект, очередь, адрес или технический номер события. Если демонстрационный генератор получает служебный заголовок, слой данных заменяет его на уникальное событийное название по метрике, рабочему контуру и пакету работ;
- `listText` — расширенное описание для компактной карточки события; оно может быть длиннее видимой области, но карточка сохраняет фиксированную высоту и обрезает текст существующим line-clamp;
- `detailText` — структурированное описание для детальной карточки события в drawer; содержит блоки `Ключевой сигнал`, `Данные и источник`, `Расчетное влияние`, `Связанный контекст`, `Рекомендуемое действие`.

Оба представления могут содержать inline-акценты в формате `**...**`. Визуальный слой преобразует эти акценты в `strong` с `font-weight: 500`. Это правило относится к демонстрационным данным прототипа и должно сохраняться до появления реального AI-генератора заголовков и описаний событий.

## Источники событий

Каталог источников событий хранится в `app-data.js` в массиве `eventSources`. Каждый источник содержит идентификатор, отображаемое имя, иконку и визуальную тему для карточки события.

Объект `theme` может содержать `chipBg`, `chipBgEnd`, `iconBg`, `iconColor` и `textColor`. Эти значения принадлежат справочнику источников и не должны задаваться отдельными исключениями для конкретных карточек.

Событие может ссылаться на один источник через `sourceId` или на несколько источников через `sourceIds`. В этом случае view model формирует `sources`, `sourceCount` и `isSourceAggregator`, а компонент карточки отображает агрегированную индикацию нескольких источников.

В текущем прототипе около 30% событий получают несколько источников демонстрационно, чтобы проверить интерфейс агрегированных событий. Реальная логика формирования таких событий должна появиться на будущем AI/ML-этапе.

Для multi-source события view model формирует `sources`, `sourceCount` и `isSourceAggregator`; количество demo-источников находится в диапазоне 2–5. Это только правило наполнения прототипа, а не промышленная логика агрегации.

## Задачи и ответственные

`task-data.js` реализует текущий прототип связи `Event 1:N Task`. Задача содержит `sourceEventId` и `projectId`, поэтому не смешивается с задачами других событий и остается доступной при переключении контекста в пределах одной загрузки страницы.

Справочник содержит 14 демонстрационных ответственных. Каждая запись хранит ФИО, инициалы, роль, должность, email, пол и путь `avatarSrc` к низкоразмерному photo-like face-only PNG `42×42px` с минимальным светлым фоном в `assets/images/assignees/` для модального окна команды проекта. На текущем этапе ответственные доступны всем проектам через wildcard-членство только для проверки dropdown и окна команды проекта. Это не промышленная модель сотрудников, ролей или доступа. Постоянное хранение задач, backend, история статусов и изменений, права и реальная принадлежность сотрудника проекту относятся к будущей реализации.

## Пользовательский путь

Пользователь выбирает узел в левом дереве. `project-structure.js` формирует активный контекст. Затем `app-data.js` возвращает события, финансовые метрики и строительные показатели только для этого контекста.

## Правило расчетной логики

Структура дерева метрик и арифметическая логика расчета не должны смешиваться в одном понятии.

Дерево метрик отвечает за декомпозицию: какие показатели являются родительскими, какие дочерними и как пользователь перемещается по структуре. Арифметическая логика отвечает за расчет: какие дочерние показатели прибавляются, какие вычитаются, какие значения агрегируются и какие параметры считаются производными.

Если в будущем появится отдельный файл или внешний источник вроде `canonical_structure_definition`, он должен описывать граф декомпозиции, но не обязан хранить всю арифметику. Правила сложения, вычитания, агрегации и прогнозного влияния должны быть зафиксированы в отдельном источнике проекта: в `src/data/README.md`, профильной документации метрик и соответствующих расчетных функциях слоя данных.

Документ нужно обновлять, если:
