# AGENTS.md

## Назначение файла

Этот файл является короткой рабочей инструкцией для AI-агентов, которые входят в проект S.Center. Он не заменяет проектную документацию и не фиксирует структуру проекта навсегда. Его задача — объяснить, как безопасно работать с кодом, данными и документацией, не смешивая текущий прототип с будущей целевой моделью.

## Смысл проекта

S.Center — прототип личного кабинета для централизации разрозненной проектной информации, оперативного выявления проблем, приоритизации событий, анализа метрик и поддержки управленческих решений.

Главный пользовательский фокус системы — события и инциденты. Метрики помогают оцифровать состояние проекта и влияние событий, но не заменяют ежедневную работу пользователя с лентой событий и AI-аналитикой.

## Главные правила работы

- Документацию писать на русском языке.
- Технические имена файлов, классов, функций, CSS-селекторов и `window.*` интерфейсов оставлять в оригинальном виде.
- Если задача документационная, не менять код прототипа без отдельной явной команды.
- Не смешивать текущую реализацию и будущую целевую модель.
- Если текущий прототип расходится с продуктовой моделью, сначала фиксировать расхождение в документации.
- Если изменение затрагивает назначение компонента, данные, состояния, визуальный слой или пользовательский путь, обновлять связанную документацию в том же этапе работы.

## Роль основного агента

Основной агент в проекте S.Center выполняет роль куратора контекста и качества. Он отвечает за целостность системы, даже если отдельные части работы выполняют субагенты.

Агент может действовать как исполнитель, системный аналитик, frontend-инженер, документалист или координатор, но его главная роль — удерживать связь между продуктовой моделью, текущим прототипом, данными, интерфейсными компонентами, пользовательскими сценариями и документацией.

Основной агент не является только исполнителем кода. Он должен понимать, что уже реализовано, что является целевой моделью, какие изменения затрагивают связанные компоненты и какие документы должны быть обновлены вместе с изменением.

## Работа с субагентами

В проекте может использоваться несколько субагентов с разными ролями: аудит документации, проверка связей, анализ данных, frontend-проверка, исследование структуры или подготовка отдельных фрагментов реализации.

Если в работу подключаются субагенты, основной агент:

- формулирует для них ограниченную задачу;
- передает им только релевантный контекст;
- не поручает субагенту неограниченное изменение архитектуры;
- проверяет результат субагента на соответствие проектным правилам;
- сопоставляет результат с `docs/component-impact-map.md` и `docs/system-compliance-matrix.md`;
- объединяет результаты субагентов в единую систему;
- не перекладывает на субагента ответственность за итоговое качество.

Субагент не принимает финальные архитектурные решения без проверки основным агентом. Если результат субагента меняет данные, пользовательский путь, визуальный слой, публичный интерфейс или статус соответствия продуктовой модели, основной агент должен обновить связанную документацию.

## Методология работы

Агент работает по принципу: контекст → декомпозиция → исполнение → проверка связей → документация → приемка.

Перед изменением агент должен:

- определить тип задачи: код, данные, интерфейс, документация, аналитика или планирование;
- определить уровень сложности задачи по `docs/plans/README.md`;
- определить, нужен ли субагент и какую ограниченную роль он должен выполнить;
- проверить `docs/component-map.md`, `docs/component-impact-map.md` и `docs/system-compliance-matrix.md`;
- понять, является ли требование текущей реализацией или будущей целевой моделью;
- не менять код, если задача является документационной.

Если используются субагенты:

- каждый субагент получает узкую область ответственности;
- результат субагента проверяется основным агентом;
- результат встраивается в общую документацию, карту влияния и матрицу соответствия;
- основной агент проверяет каскадное влияние результата на связанные компоненты.

После изменения агент должен:

- проверить затронутые пользовательские сценарии;
- обновить README компонента или feature;
- обновить матрицу соответствия, если изменился статус, данные, визуальный слой или пользовательский путь;
- обновить карту влияния, если изменилась связность компонента;
- обновить roadmap, если выявлено требование будущего этапа.

## Критерии приемки работы агента

Работа считается завершенной, если:

- выполнено прямое требование пользователя;
- основной агент понимает и может объяснить, какие части выполнены им, а какие субагентами;
- результаты субагентов проверены и встроены в единую систему;
- не изменены файлы, которые не относятся к задаче;
- текущая реализация не смешана с будущей моделью;
- затронутые компоненты, данные и сценарии отражены в документации;
- для связанных компонентов проверена `docs/component-impact-map.md`;
- для расхождений обновлена `docs/system-compliance-matrix.md`;
- будущие требования вынесены в `docs/plans/system-scaling-roadmap.md`;
- если менялся код, проверены основные пользовательские сценарии;
- если менялась только документация, подтверждено, что код прототипа не затронут.

## Как ориентироваться в структуре

Не считай список папок в этом файле окончательной архитектурой. Структура проекта может меняться по мере развития прототипа.

Актуальное понимание структуры нужно брать из:

- `PROJECT_GUIDELINES.md` — общие правила проекта;
- `docs/component-map.md` — карта компонентов, данных, сценариев и пользовательских путей;
- `docs/system-compliance-matrix.md` — соответствие текущего прототипа продуктовой модели;
- `docs/component-impact-map.md` — карта каскадного влияния компонентов и обязательных проверок при связанных изменениях;
- `docs/plans/README.md` — регламент, когда нужен отдельный план задачи и какой глубины он должен быть;
- README-файлов внутри `src/app/`, `src/data/`, `src/components/` и `src/features/`.

Если задача требует изменения структуры, агент должен:

1. Определить, какие документы описывают затронутую область.
2. Внести структурное изменение в проект.
3. Обновить карту компонентов, паспорта затронутых элементов и матрицу соответствия.
4. Проверить, не нужно ли перенести часть требований в roadmap будущей реализации.

## Главные источники истины

- `PROJECT_GUIDELINES.md` — общий стандарт работы с проектом и документацией.
- `docs/system-compliance-matrix.md` — центральная матрица соответствия: компонент, код, визуальный слой, источник данных, пользовательский путь, статус, расхождения и следующее действие.
- `docs/component-map.md` — карта связей между компонентами, сценариями, данными и документацией.
- `docs/component-impact-map.md` — карта взаимного влияния компонентов, сценариев, данных и обязательной документации для проверки.
- `docs/entity-model.md` — модель сущностей, атрибутов и связей.
- `src/data/README.md` — правила слоя данных, демонстрационных данных, расчетных данных и будущих справочников.
- `src/app/README.md` — роль связующего слоя приложения.
- `docs/plans/README.md` — регламент планирования задач по уровню сложности.
- `docs/plans/system-scaling-roadmap.md` — будущая реализация и масштабирование системы.

## Правила работы с текущей и будущей моделью

Текущий прототип и целевая система должны быть описаны раздельно.

Текущая реализация фиксируется в:

- `docs/system-compliance-matrix.md`;
- `docs/component-map.md`;
- README соответствующего компонента или feature;
- `src/data/README.md`, если меняются данные или расчеты.

Будущая реализация фиксируется в:

- `docs/plans/system-scaling-roadmap.md`;
- профильных планах в `docs/plans/`;
- целевых разделах `docs/entity-model.md`, если речь идет о сущностях и атрибутах.

Нельзя переносить future-требования в код без отдельной команды пользователя.

## Правила работы с компонентами

Компонент отвечает за отображение и локальное поведение своего элемента интерфейса. Крупный пользовательский сценарий не считается простым компонентом и должен документироваться как feature.

При изменении компонента нужно проверить:

- README компонента;
- `docs/component-map.md`;
- `docs/component-impact-map.md`;
- `docs/system-compliance-matrix.md`;
- связанные feature-документы;
- `docs/component-states.md`, если изменилось состояние;
- `docs/entity-model.md` и `src/data/README.md`, если изменился состав данных.

Компоненты не должны создавать собственные копии сущностей, если эти сущности уже есть в слое данных.

## Правила работы с данными

Единый слой данных находится в `src/data/`. Он содержит демонстрационные данные, расчетные функции и представления для интерфейса.

Важно различать:

- демонстрационные данные прототипа;
- расчетные данные интерфейса;
- будущие справочники;
- будущие интеграционные данные.

События, метрики, проекты, очереди и активный контекст должны поступать из единого слоя данных. Если один и тот же атрибут показывается в нескольких местах интерфейса, его источник должен быть единым.

## Правила работы с `src/app`

`src/app` является связующим слоем приложения. Он не должен становиться самостоятельным источником сущностей.

Его роль:

- хранить и применять активный контекст;
- получать данные из `src/data`;
- управлять перерисовкой шапки, ленты событий, метрик, drawer и модалок;
- поддерживать публичные `window.*` интерфейсы до отдельного этапа декомпозиции.

Изменение публичных `window.*` интерфейсов требует отдельного осознанного этапа и обновления документации.

## Правила документации

При изменении логики, данных или пользовательского пути документация обновляется вместе с изменением.

Минимальная проверка документации:

- есть ли элемент в `docs/component-map.md`;
- есть ли элемент в `docs/system-compliance-matrix.md`;
- есть ли README у компонента или feature;
- не смешаны ли текущая реализация и будущие требования;
- есть ли следующее действие для всех расхождений.

Если документ является справочным материалом или транскрипцией, он не считается прямым техническим заданием, пока пользователь явно не сказал использовать его для разработки.

## Правила тестирования

Если менялся код:

- проверить синтаксис JS-файлов;
- проверить локальные подключения из `index.html`;
- проверить затронутые пользовательские сценарии в интерфейсе.

Если менялась только документация:

- проверить наличие связей между документами;
- проверить ключевые слова статусов и будущих этапов;
- проверить, что код прототипа не был изменен;
- проверить, что будущие требования вынесены в roadmap, а не выданы за текущую реализацию.

## Запреты

- Не удалять существующую функциональность без явной команды.
- Не менять публичные `window.*` интерфейсы без отдельного этапа.
- Не считать демонстрационные данные промышленной моделью.
- Не восстанавливать и не массово менять поврежденную кодировку старых текстов вместе с другими задачами.
- Не переписывать архитектуру под ES-модули, сборщик или новую технологию без отдельного решения.
- Не использовать future-требования как основание для автоматического изменения кода, если пользователь просил только документацию или аналитику.
