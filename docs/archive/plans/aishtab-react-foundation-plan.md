# План: эталон, дизайн и пилот React для AIShtab

Тип — подэтап перехода, P0–P2. Входит в [главный план](aishtab-react-redesign-plan.md) и подчиняется [регламенту](../../plans/README.md).
Статус — завершен. Пользователь принял React-прототип, основной локальный запуск переключен. Документ хранится как история перехода.

## Goal

Закрепить воспроизводимый эталон, согласовать интерфейс и архитектуру React-версии, затем проверить их на рабочем пути от выбранного проекта до BI-графика.

## Context

Источник текущего поведения — локальный нативный прототип. Области сверки — [контекст](../../context-behavior.md), [связующий слой](../../../src/app/README.md), [данные](../../../src/data/README.md), [карта компонентов](../../component-map.md) и [матрица соответствия](../../system-compliance-matrix.md). Для UX-решений можно использовать подтвержденные материалы [плана UX-бенчмарка](../../plans/aishtab-ux-benchmark-user-journeys-plan.md); этот план имеет собственную приемку.

## Scope

Инвентаризация действующих сценариев, карта изменений, согласование дизайна и общих контрактов. Технический пилот охватывает оболочку и дерево контекста, минимальный путь к карточке события, саму карточку и общий BI-график с прогнозом.

## Out of Scope

Остальные ветки реализации входят в [P3](aishtab-react-feature-migration-plan.md). Подключение новых источников и замена действующей публикации остаются за пределами пилота.

## Constraints

Два локальных запуска доступны для сравнения. Все принятые решения привязаны к конкретным сценариям. Общие контракты публикуются для участников P3 с перечнем файлов и владельцем изменений.

## Impact

Шапка, дерево навигации и события зависят от единого контекста. Карточка и BI используют устойчивые идентификаторы события и метрики. Структура BI должна поддерживать второй вход из дерева в P3. Изменения общего состояния и слоев проверяются по [карте влияния](../../component-impact-map.md).

## Steps

### P0. Эталон и карта изменений

1. Указать ревизию Git и зафиксировать, есть ли в рабочем дереве собственные изменения пользователя. Для сравнения выбрать воспроизводимый набор кода, данных и ресурсов. Запустить нативный прототип по [инструкции](../../../README.md), проверить локальные зависимости и отметить внешние ресурсы, необходимые для повторения. В текущей точке входа есть внешние шрифты и Lucide с версией `@latest`. Для проверки восстановления в P5 установить, как воспроизвести эти зависимости.
2. Пройти активные области по [карте](../../component-map.md), локальным паспортам и [группам сценариев для приемки](aishtab-react-acceptance-cutover-plan.md). Для каждого сценария записать устойчивый ID, исходный контекст и данные, действия, фактический результат, ожидаемый контракт и ссылку на владельца. Добавить ключевые скриншоты по стабильному размеру окна. Для особых состояний задать подходящие тестовые данные или способ воспроизведения.
3. Пометить по каждому ID решение «сохранить», «изменить оформление», «изменить сценарий», «вывести по согласованию». Отдельно отметить наблюдаемые дефекты, расхождения источников, демонстрационные ограничения и вопросы. Назначить владельца и указать конкретный пакет, который зависит от ответа. Сверить с пользователем спорные изменения. Уточнить объем пакетов и очередность.

Выход P0 — зафиксированная исходная версия, воспроизводимые проверки по активным областям, карта изменений и список решений по пакетам. Можно проектировать P1, если ясны границы пилота.

### P1. Визуальное направление и общая архитектура

1. Подготовить визуальные решения общей оболочки и пилотного сценария. Показать навигацию, типографику, плотность, основные действия, пустое состояние, drawer и вложенный график. Пользователь принимает направление и перечень допустимых изменений поведения. Для каждого следующего пакета уточнить решение до его назначения.
2. Сопоставить существующие токены и компоненты с выбранным дизайном. Зафиксировать правила использования дизайн-системы и разделение между общими компонентами и представлениями разделов. Уточнить используемые размеры окна и браузеры по реальной аудитории.
3. Выбрать инструменты сборки, версии и инструкции для воспроизводимого запуска. Оформить архитектурное решение с точками входа, границами общей оболочки и разделов, правилами импорта, хранением исходников и способом сборки для текущего контура публикации. React — выбранное направление, инструменты сборки и необходимость дополнительных библиотек определяются здесь.
4. Зафиксировать владельцев состояния и интерфейсы потребителей. Общий контекст хранит уровень и устойчивый ключ, разделы получают данные через единый источник, локальное состояние остается у владельца сценария. Определить жизненный цикл drawer и модалок, обработку `Escape`, фокус, прокрутку, отмену устаревшего ответа. Составить перечень `window.*` с текущими вызывающими сторонами. Для каждого определить совместимость на переходе или замену после перевода всех потребителей. Назначить единый источник демонстрационных данных и повторно используемых расчетов.

Выход P1 — принятый дизайн пилота, решения по сборке и архитектуре, интерфейсы данных, состояния и межкомпонентного взаимодействия. Только подтвержденные правила передаются в P2.

### P2. Сквозной пилот

1. Собрать отдельно запускаемую оболочку React, контекстное дерево, шапку, минимальную ленту и карточку события. Подключить существующие демонстрационные данные через согласованный слой доступа.
2. Реализовать общий BI-график. Проверить идентификатор из карточки, план, факт, переключение прогноза, hover-подсказку и закрытие. Проверить публичный интерфейс, который пакет дерева будет вызывать в P3.
3. В одном проекте и одной очереди пройти путь «контекст → событие → график → возврат». Переключить контекст и проверить согласованность шапки, ленты и графика. На широкой и узкой контрольных ширинах проверить расположение слоев, `Escape`, каскадное закрытие и возврат фокуса. Сопоставить результаты с эталоном и принятым дизайном.
4. Устранить выявленные препятствия повторному использованию. Зафиксировать готовые интерфейсы для P3, перечень передаваемых компонентов и фактические усилия по пилоту. Обновить оценки и назначить первую очередь пакетов.

## Acceptance Criteria

- Реестр P0 содержит проверяемые записи по активным областям. Каждое расхождение имеет статус и владельца решения.
- Дизайн пилота и изменения поведения подтверждены пользователем. Общие интерфейсы доступны исполнителям P3 и подкреплены работающим пилотом.
- Обе версии запускаются по своим инструкциям. Пилот воспроизводим на одинаковых данных, проходит функциональную и визуальную проверку и сохраняет корректный контекст при возврате из BI.

## Documentation Updates

Записать результаты сверки в реестр перехода. После принятия P2 описать запуск, архитектурные решения и принятые интерфейсы у владельцев инструментария, оболочки, данных, карточки и BI. Основной нативный запуск по-прежнему указан как действующий до P5.
