# План: редизайн AIShtab и переход на React

Тип — план макро-задачи. Временной слой — переходный. Регламент — [docs/plans/README.md](../../plans/README.md).
Статус — завершен. Пользователь принял React-прототип, основной локальный запуск переключен. Документ хранится как история перехода.
Ответственный за общий план, интеграцию и техническую приемку — основной исполнитель. Продуктовые и визуальные решения принимает пользователь.
План закрывается после финальной приемки, смены основной версии и передачи подтвержденных контрактов постоянным владельцам.

## Goal

Сделать React-версию AIShtab с согласованным редизайном, проверяемой преемственностью работающих сценариев и воспроизводимым переходом с текущей версии. Подготовить отдельные пакеты работ для последовательного или параллельного исполнения и независимо проверить их перед объединением.

## Context

На момент начала миграции нативный прототип запускался из корневого `index.html` через `node scripts/serve-prototype.mjs`. Оба файла доступны в Git-метке `aishtab-native-final`. Он подключает CSS и обычные JavaScript-скрипты. [`src/app`](../../../src/app/README.md) координирует контекст, перерисовку и интерфейсы `window.*`. [`src/data`](../../../src/data/README.md) владеет общими демонстрационными сущностями и расчетами. Активные поверхности — «Сводный дашборд», «Сводка» и «Объекты». Основной пользовательский путь начинается с работы с событиями.

Начальная статическая сверка проведена по точке входа, паспортам и картам. На момент подготовки плана девять проверок существующего набора прошли. Полный браузерный реестр с результатами для конкретных демонстрационных данных формируется в P0. Если код, паспорт и карта расходятся, P0 фиксирует фактическое проявление и владельца решения. Например, в отдельных описаниях BI есть формулировка «action-кнопка»; код и паспорт дерева указывают на основную область строки. Способ открытия графика подтверждается в браузере и закрепляется в реестре.

## Scope

- Обследование активного прототипа и карта изменений по сценариям и экранам. Для каждого — сохранить поведение, изменить оформление, переработать сценарий или вывести из активной версии по продуктовому решению.
- Визуальное направление, общая оболочка React, правила состояния и данных, сквозной пилот, перенос всех принятых активных пакетов.
- Независимая приемка пакетов, интеграционная проверка после каждого объединения, полный финальный прогон и перевод рабочего запуска на React.
- Сохранение воспроизводимой нативной версии в Git и контролируемый вывод файлов, нужных только старому интерфейсу.

## Out of Scope

Подключение промышленных данных, методики прогноза, backend, постоянное хранение задач, RBAC, реальный AI-провайдер, новые разделы со статусом «Скоро», возврат изолированных модулей. Такие работы остаются в [roadmap](../../plans/system-scaling-roadmap.md) и профильных планах. Выбор нового вида дерева метрик остается продуктовым решением. Имеющиеся концепты служат материалом для обсуждения.

## Constraints

- Нативный прототип остается доступным по текущей точке входа до приемки. React получает собственный локальный запуск и сборку. Точные пути и команды определяет P1.
- Сценарии сравниваются на одинаковых идентификаторах и демонстрационных данных. Проверяются различия бизнес-юнита, проекта и очереди. Один показатель или объект имеет одного владельца данных.
- Работоспособное поведение переносится по проверенному реестру. Изменения внешнего вида и сценария сверяются с принятым дизайн-решением. Известные дефекты и расхождения ведутся отдельно от ожидаемого поведения.
- Изменение публичных `window.*` имеет выделенный шаг с перечнем потребителей и проверками. Разработка новых областей выполняется по согласованным интерфейсам. Владелец общей оболочки интегрирует изменения в пересекающихся файлах.
- Права на публикацию и вывод файлов из активной ветки проверяются на этапе переключения. Его вход — финальная продуктовая приемка.

## Steps

Указание пользователя к реализации — сохранить концепцию и дизайн текущего прототипа, выполнить перенос активных компонентов на React и точечные улучшения взаимодействий. Существенные изменения интерфейса будут отдельными задачами. Состав сборки и реализованные улучшения описаны в [паспорте React-версии](../../../react/README.md).

| Этап | Вход | Результат и условие перехода |
| --- | --- | --- |
| P0. Эталон и карта изменений | Согласование плана | Воспроизводимый эталон, реестр сценариев с данными и наблюдениями, решения или вопросы для P1 |
| P1. Дизайн и архитектура | P0 | Пользователь принял направление и изменения пилота. Определены запуск, общие контракты и границы пакетов |
| P2. Пилот | P1 | Цепочка «проект → событие → BI-график → возврат» принята в браузере и по данным. Утверждены общие интерфейсы для потоков переноса |
| P3. Перенос пакетов | P2, решение по дизайну каждой назначаемой области | Каждый пакет принят отдельно. В общей сборке проверены затронутые стыки и постоянная документация |
| P4. Финальная приемка | Все пакеты P3 приняты | Полный контрольный прогон по реестру, исправления, повторные проверки, решение пользователя о приемке |
| P5. Переключение | P4, проверенный снимок старой версии и согласованное переключение | React — основной запуск. Проверен доступ к эталону по Git-метке, согласован выпуск, план закрыт |

- [P0–P2. Эталон, дизайн, архитектура и пилот](aishtab-react-foundation-plan.md).
- [P3. Пакеты переноса, зависимости и исполнители](aishtab-react-feature-migration-plan.md).
- [P4–P5. Финальная приемка, Git-снимок и переключение](aishtab-react-acceptance-cutover-plan.md).

### Управление исполнением

- Стартовый ориентир — один основной исполнитель на P0–P2. После пилота план рассчитан на две независимые реализации одновременно плюс основной исполнитель на интеграции и приемке, если есть доступные кандидаты. Третий параллельный пакет открывается только при независимых границах и достаточной емкости приемки. При одном исполнителе сохраняется очередность пакетов и отдельно выделяется проверочный проход.
- До каждого запуска пакета фиксируются ответственный, рабочие файлы, зависимости, ожидаемый результат, оценка и проверяющий. Календарный прогноз строится после P0 по доступной загрузке, последовательным зависимостям и времени на исправления и интеграцию. После пилота оценки уточняются по фактическому усилию.
- Владелец пакета передает изменения, команды запуска, результаты проверок и открытые отклонения. Основной исполнитель повторяет ключевые проверки сам, принимает или возвращает пакет на доработку и объединяет принятые результаты. При совмещении ролей отмечается, кто выполнял повторную проверку. Пользователь подтверждает визуальное направление, изменения поведения и финальный результат.

## Acceptance Criteria

- Все активные области имеют решение и сценарии проверки. Каждое отличие React от эталона привязано к согласованному изменению или зарегистрированному дефекту.
- Пилот и все пакеты прошли свои критерии. Сквозные сценарии и локальные состояния прошли проверку на интегрированной сборке. Подтверждены функция, данные, связи и визуальное соответствие.
- React запускается по задокументированной инструкции. Рабочую нативную версию можно запустить из сохраненной точки Git. Состояние публикации явно зафиксировано.
- Постоянная документация синхронизирована с принятой версией. Все блокирующие расхождения закрыты либо выпуск отложен.
