# Регламент планирования задач

## Назначение

Этот документ описывает, когда в проекте S.Center нужен отдельный план задачи, какой глубины он должен быть и где его хранить. Цель регламента — не раздувать контекст для мелких правок и при этом не начинать сложные изменения без ясной цели, ограничений, карты влияния и критериев приемки.

План является задачным слоем контекста. Он дополняет, но не заменяет:

- `AGENTS.md` — инвариантные правила работы агента;
- `PROJECT_GUIDELINES.md` — общий стандарт проекта;
- `docs/component-impact-map.md` — каскадное влияние компонентов;
- `docs/system-compliance-matrix.md` — соответствие текущего прототипа продуктовой модели;
- `docs/plans/system-scaling-roadmap.md` — будущие этапы масштабирования.

## Существующие планы

| Документ | Тип | Статус | Назначение |
| --- | --- | --- | --- |
| `metrics-real-data-integration-plan.md` | План будущей интеграции | Требует продуктового решения | Реальные источники, методика, качество данных, права и уровни агрегации дашборда метрик. |
| `ai-chat-provider-actions-plan.md` | План будущей интеграции | Требует продуктового и security-решения | Промышленный provider, хранение, права, аудит и подтверждаемые действия AI-чата. |
| `system-scaling-roadmap.md` | Roadmap | Постоянно актуализируется | Будущая реализация элементов, которые описаны продуктово, но не реализованы полностью в текущем прототипе. |

Завершенные планы находятся в `../archive/plans/README.md`. Все новые планы в `docs/plans/` должны соотноситься с этим регламентом. Если документ является конкретным планом задачи, в начале файла нужно указать, что он подчиняется `docs/plans/README.md`. Если документ является roadmap, нужно явно указать, что он не заменяет конкретные планы задач.

## Уровни сложности задач

| Уровень | Когда применяется | Нужен ли отдельный файл плана |
| --- | --- | --- |
| Микро-задача | Локальная визуальная или текстовая правка без изменения данных, логики, пользовательского пути и связей. | Нет. Достаточно прямого исполнения по правилам `AGENTS.md`. |
| Малая задача | Правка одного компонента или документа, где влияние понятно и ограничено. | Обычно нет. Достаточно краткого чек-листа в диалоге и обновления README/матрицы при необходимости. |
| Средняя задача | Затрагивается компонент с зависимостями, feature, данные одного сценария или несколько документов. | По ситуации. Можно создать короткий план в `docs/plans/`, если есть риск потерять контекст. |
| Сложная задача | Меняется структура проекта, `src/data`, `src/app`, публичные `window.*`, несколько компонентов, пользовательский путь или расчетная логика. | Да. Нужен отдельный `docs/plans/<task-name>.md` до реализации. |
| Макро-задача | Рефакторинг, новая подсистема, интеграция, AI/ML, роли и доступы, масштабирование модели данных. | Да. Нужен полноценный план или SPEC и подтверждение пользователя перед исполнением. |

## Когда план обязателен

Отдельный план обязателен, если выполняется хотя бы одно условие:

- меняется структура проекта;
- меняется слой данных `src/data`;
- меняется связующий слой `src/app`;
- меняются публичные `window.*` интерфейсы;
- затрагиваются несколько компонентов или features;
- меняется пользовательский путь;
- меняется расчетная логика финансовых или строительных метрик;
- появляется новая сущность, справочник или интеграционный источник;
- нужно подключать субагентов;
- есть риск смешать текущую реализацию и будущую целевую модель;
- задача требует подтверждения пользователя до изменения кода.

## Adaptive Routing

Перед началом работы агент должен определить уровень задачи и выбрать глубину планирования.

Решение принимается по трем вопросам:

1. Затрагивает ли задача только один локальный элемент или несколько связанных областей?
2. Меняет ли задача данные, состояния, пользовательский путь, расчет или публичный интерфейс?
3. Нужно ли отделить текущую реализацию от будущей модели?

Если ответ на второй или третий вопрос положительный, нужно проверить `docs/component-impact-map.md` и `docs/system-compliance-matrix.md`. Если влияние выходит за один компонент, план становится обязательным или как минимум желательным.

## Plan → Execute → Reset

Для сложных и макро-задач используется дисциплина:

1. `Plan` — агент анализирует контекст, читает связанные документы и формирует план без изменения кода.
2. `Approve` — пользователь подтверждает план или уточняет его.
3. `Execute` — агент выполняет задачу в рамках утвержденного плана.
4. `Verify` — агент проверяет код, UI-сценарии, документацию и каскадные связи.
5. `Reset` — агент фиксирует результат, переносит будущие требования в roadmap и не держит устаревший план как активный источник истины.

Если пользователь явно просит сразу реализовать утвержденный план, этап `Approve` считается выполненным для этого плана.

## Шаблон плана

Новый план в `docs/plans/` должен использовать этот состав. Для средней задачи некоторые разделы могут быть короткими, но их смысл должен быть сохранен.

```md
# План: <название задачи>

## Goal

Что нужно получить в результате.

## Context

Какие компоненты, данные, документы, пользовательские сценарии и ограничения уже существуют.

## Scope

Что входит в задачу.

## Out of Scope

Что не делаем в этом этапе, чтобы не смешать текущую задачу с будущими требованиями.

## Constraints

Что нельзя ломать: публичные интерфейсы, визуальную концепцию, текущую структуру данных, сценарии, документацию.

## Impact

Какие компоненты, features, данные и документы могут быть затронуты. Здесь нужно свериться с `docs/component-impact-map.md`.

## Steps

Последовательность выполнения.

## Acceptance Criteria

Как понять, что задача выполнена.

## Documentation Updates

Какие README, карты, матрицы или планы нужно обновить.

## Verification

Какие проверки выполнить: синтаксис, UI-сценарии, локальные подключения, документационные связи.
```

## Критерии хорошего плана

План считается пригодным для исполнения, если:

- цель сформулирована как конкретный результат;
- понятно, какие файлы и области затрагиваются;
- явно указано, что не входит в задачу;
- перечислены ограничения и риски;
- указан каскадный impact по компонентам;
- есть критерии приемки;
- есть список документации, которую нужно обновить;
- будущие требования не смешаны с текущей реализацией.

## Работа с субагентами

Если задача требует субагентов, план должен явно указать:

- какие роли нужны;
- какую ограниченную область получает каждый субагент;
- какой результат должен вернуть субагент;
- какие документы и проверки остаются ответственностью основного агента;
- как результат субагента будет встроен в общую матрицу и карту влияния.

Субагент не должен менять архитектурный статус элемента без проверки основным агентом.

## Skills и будущая автоматизация

На текущем этапе отдельный skill для планирования не создается. Регламент в этом документе является источником правил.

Skill может быть создан позже, если появится повторяемая операция, например:

- создать план сложной задачи по стандарту S.Center;
- провести аудит компонента по карте влияния;
- обновить документацию после изменения компонента;
- проверить соответствие реализации матрице;
- подготовить задачу для субагента.

До появления такого устойчивого повторяемого сценария планирование выполняется через этот документ и правила `AGENTS.md`.

## Когда обновлять регламент

Этот README нужно обновлять, если:

- меняется подход к планированию;
- появляется новый тип задач;
- вводится отдельный skill или slash-команда;
- меняется роль субагентов;
- меняются критерии приемки планов;
- меняется структура `docs/plans/`.
